## 1. 목표와 비목표

**목표.** #149 가 만든 ISM 2층 폭발의 **연출 깊이**를 올린다. 드로우콜 상수성은 그대로 유지한다.

두 갈래다.

**(a) 코어 톤.** 흰색 포화를 없애 주황 불덩이로 읽히게 한다. 머티리얼 파라미터 기본값만 바꾼다 — C++ 0줄, 드로우콜 변화 0.

**(b) 연기 대역.** 3번째 ISM 층(큰 반투명 어두운 구체)을 더해 실루엣에 부피를 준다. 드로우콜 +2 상수, 동시 개수와는 여전히 무관.

**비목표.**
- 드로우콜 상수성 재검증 — #149 §9.1 에서 끝났다. 이 작업은 상수값이 4 → 6 으로 오르는 것만 확인한다
- 오버드로우 제거 — 반투명 층이 하나 늘어 픽셀 비용은 **올라간다**(§8). 측정으로 감시할 뿐 줄이지 않는다
- 연출 종류 분기(피격 / 착지), NDC, SubUV 플립북 — 전부 범위 밖(§10)

## 2. 문제

`ScreenShot00161` / `00162` (실 RHI 1600x900, 동시 63~128) 관찰. 두 가지가 겹쳐 납작하다.

### 2.1 코어가 흰색으로 포화된다

`M_REExplosionCore` 는 언릿 이미시브에 `Strength` 기본값이 **3.0** 이다. 진행도 0 에서:

```
emissive = Color(1.0, 0.90, 0.55) * 3.0 * (1 - 0)  =  (3.00, 2.70, 1.65)
```

세 채널이 전부 1.0 을 크게 넘는다. 톤매퍼를 거치면 채널 비율이 뭉개져 흰색으로 읽히고, 블룸까지 얹혀 흰 덩어리가 된다.

### 2.2 주황 그라데이션은 애초에 보이지 않는 자리에 있다

`Color`(흰-노랑) → `ColorB`(주황-적) 를 **진행도로 보간**하는데, 같은 진행도가 **밝기 감쇠**(`1 − 진행도`)의 분모이기도 하다. 즉 색이 주황으로 물드는 만큼 정확히 그만큼 어두워진다:

| 진행도 | 색 | 밝기 배율 | 화면 |
|---:|---|---:|---|
| 0.0 | 흰-노랑 | 1.00 | 밝다 — 보인다 |
| 0.5 | 중간 | 0.50 | 절반 |
| 1.0 | 주황-적 | **0.00** | 안 보인다 |

**주황이 최대치에 도달하는 순간 알파가 0 이다.** `Strength` 를 내리면 흰색 포화는 사라지지만 이 상관관계는 남는다. 그래도 (a) 를 먼저 하는 이유는 포화가 사라지면 노랑-주황 중간 구간이 살아나 절반은 해결되기 때문이고, 나머지 절반(그라데이션 알파 리맵)은 그래도 부족할 때 손대는 별건이다(§10).

### 2.3 층이 둘뿐이라 부피가 없다

코어(구체)와 링(평면)만 있다. 구체 하나가 커졌다 사라지는 실루엣이라 "폭발"보다 "커지는 공"으로 읽힌다. 팩 폭발이 입체로 보였던 이유는 **깊이·크기·투명도가 다른 층이 여러 겹 겹쳐 있어서**였다(#149 §4.1). 층이 2 면 겹칠 것이 없다.

## 4. 결정

### 4.1 (a) 층별 Strength 인자 분리

`--strength` 하나를 `--core-strength` / `--ring-strength` / `--smoke-strength` 로 쪼갠다.

이유는 **링이 포화되는 것은 의도**이기 때문이다. 링은 얇은 원환이라 픽셀 몇 줄로 충격파를 읽혀야 하고, HDR 1.0 위로 올려 블룸을 태우는 것이 마커(`M_ArenaMarker`, `Color = (3, 0.15, 0.15)`)와 같은 기존 규약이다. 코어만 내리는 방법이 지금은 없다.

공유 인자를 유지하고 셋 다 같이 내리는 안은 뺐다 — 링이 죽는다.

### 4.2 (b) 연기 층의 수명은 머티리얼 페이드 커브로 만든다

"코어보다 늦게까지 남는다"를 **C++ 수명이 아니라 알파 커브**로 구현한다.

| 층 | 알파 |
|---|---|
| 코어 / 링 | `1 − p` (선형 소멸) |
| 연기 | `(1 − p³) × saturate(p × RampIn)` |

`1 − p³` 은 p=0.6 에서도 0.78 을 유지하고 끝에서 급락한다 — 코어가 0.4 로 죽어가는 동안 연기는 거의 그대로 남는다.

**대안이었던 "`ExplosionLifeSec` 을 0.8 → 1.2 로 올리고 코어/링을 먼저 죽인다"를 뺀 이유:** 진행도 분모가 바뀌면 코어·링의 반경 곡선과 감쇠 속도가 전부 바뀐다. #149 §9.1 이 판정한 룩이 통째로 무효화되고, 재판정 대상이 (b) 하나에서 셋으로 늘어난다. 커스텀데이터 슬롯을 층별로 쪼개는 안도 같은 이유로 뺐다 — 계약이 복잡해지는 대가로 얻는 것이 커브 하나다.

**따라서 커스텀데이터 계약은 불변이다.** 슬롯 1개, `[0] = 진행도`, 세 층이 같은 값을 받고 각자 해석한다.

### 4.3 연기 실루엣은 프레넬 역마스크로 흐린다

반투명 구체를 알파 상수로 그리면 **딱딱한 공 테두리**가 보인다 — §2.3 이 지적한 "커지는 공"을 하나 더 얹는 꼴이다.

`1 − Fresnel` 을 알파에 곱한다: 카메라 정면(중심)에서 1, 실루엣 가장자리에서 0. 가장자리가 배경으로 녹아 부피로 읽힌다. 노드 3개고 `M_REBullet` 이 이미 쓰는 패턴이다(`make_bullet_material.py:120`).

### 4.4 연기는 페이드-인이 필요하다

`1 − p³` 은 **p=0 에서 1** 이다. 램프 없이 쓰면 스폰 프레임에서 반경 30uu 의 어두운 구체가 최대 알파로 뜨고, 프레넬 역마스크가 하필 **중심에서 가장 불투명**하므로 그 뒤의 밝은 코어를 정확히 가린다 → **폭발이 회색으로 열린다.**

`saturate(p × RampIn)`, `RampIn = 5.0` 이면 p=0.2(0.16초)에 완전 불투명이 된다. 그 사이에 코어가 최대 밝기 구간을 지나간다.

### 4.5 기각한 대안

**연기 반경을 코어보다 크게 두고 알파만 낮춰 램프를 생략.** 낮은 알파(0.2)로도 프레넬 역마스크 때문에 중심 가림은 남고, 낮추면 연기가 아예 안 보인다. 노드 3개가 더 싸다.

**연기를 additive 로.** `make_beam_material.py:15-19` 의 되돌린 기록 — 아레나 바닥이 밝은 라벤더라 흰색으로 포화된다. 게다가 연기는 **어두워야** 하므로 additive 는 방향이 반대다.

**연기에 감산(Subtractive) 블렌드.** 어두운 연기의 정공법이지만 리포에 선례가 없고, 반투명 알파 블렌드로 `Emissive ≈ 0` 을 쓰면 같은 효과가 난다(`결과 = 거의검정 × 알파 + 배경 × (1−알파)`). 새 블렌드 모드를 들일 이유가 없다.

**4번째 층(스파크 / 잔불).** 3층으로 부족하다고 스크린샷이 말할 때만(§10).

## 5. 구조

변경 지점 **4곳**. 새 파일 0개.

### 5.1 `scripts/make_explosion_material.py`

- `_arg("strength", 3.0)` 3곳을 층별 이름으로 교체
- 파일 끝에 **연기 섹션** 추가 (`M_REExplosionSmoke`)

새 스크립트를 만들지 않는다 — 세 머티리얼이 같은 `helpers()` / `make_material()` / 진행도 계약을 공유한다. 파일이 갈리면 규약이 갈린다.

연기 그래프:

```
진행도 p ──┬─ p³ ─── 1−(·) ────────┐
           │                        ├─ × ─┐
           └─ × RampIn ─ clamp ─────┘     │
                                          ├─ × ─── Opacity 출력
   Fresnel(ExponentIn=2.0) ─ 1−(·) ───────┤
                                    Opacity 파라미터 ─┘

   Color × Strength ─────────────────────── Emissive 출력
```

이미시브에는 페이드를 곱하지 않는다 — 거의 검정이라 곱해도 화면에서 같고, 알파가 이미 소멸을 담당한다.

### 5.2 `REBulletRenderSubsystem` — ISM 3번째 통

`ExplosionSmokeISM` 추가. 기존 두 통과 **같은 설정**:

- 메시 `/Engine/BasicShapes/Sphere` (등방 구체 — §7 의 Z 스케일 함정과 무관)
- `SetCollisionEnabled(NoCollision)`
- `bAffectDynamicIndirectLighting = false`, `bAffectDistanceFieldLighting = false`
- `SetCastShadow(false)`
- `SetNumCustomDataFloats(1)`
- `SetMaterial(0, M_REExplosionSmoke)` + 로드 실패 시 `Error` 로그 (조용한 폴백 금지)

**등록 순서는 코어 → 링 → 연기.** 반투명 프리미티브 간 정렬은 컴포넌트 단위라 순서가 화면에 남는다(§7).

### 5.3 `REExplosionRenderProcessor` — 반경 상수 + Sync 호출 1쌍

기존 루프에 세 줄이 붙는다. 구조 변경 없음:

```
ExplosionSmokeRadiusStart / End 상수 추가
루프 안:  SmokeXf.Add(FTransform(회전0, E.Loc, FVector(SmokeR / EngineSphereRadius)))
루프 뒤:  SyncExplosionISM(SmokeISM, SmokeXf);
          SmokeISM->SetCustomData(0, M - 1, Cd, true);
```

`Cd` 배열은 **공유**한다 — 세 층이 같은 진행도를 받는다(§4.2).

### 5.4 데이터 흐름 (변경 없음)

```
피격/착지 → REExplosionFx::SpawnBulletExplosion   ← 시그니처 불변, 호출부 3곳 무수정
매 프레임 → REExplosionRenderProcessor::Execute
              만료 제거 → 진행도 갱신
              → 코어 / 링 / **연기** 트랜스폼 3벌 + 커스텀데이터 1벌
              → ISM 3통에 배치 반영
```

## 7. 함정

**반투명 정렬이 컴포넌트 단위다.** ISM 인스턴스끼리는 정렬되지 않고, 서로 다른 ISM 컴포넌트는 프리미티브 단위로 정렬된다. 연기 구체가 코어를 감싸므로 **연기가 코어보다 앞에 그려지면 코어가 통째로 흐려진다.** 등록 순서(코어 → 링 → 연기)와 §4.4 의 페이드-인이 완화책이고, **판정은 스크린샷 게이트다.** 무너지면 폴백은 연기 `Opacity` 를 0.25 까지 내리는 것(대가: 부피감이 줄어든다).

**ISM 비등방 스케일.** XY 를 키운 채 Z 를 1.0 미만으로 두면 인스턴스가 화면에서 통째로 사라진다(`REArcRenderProcessor.cpp:16-23`, 실RHI 이진탐색으로 확인, 원인 미상). **연기는 등방 구체라 해당 없다** — 하지만 링을 건드리면 걸린다. 링은 이 작업에서 건드리지 않는다.

**`--force` 없이는 에셋이 안 바뀐다.** 스크립트는 기존 에셋을 발견하면 중단한다. 정본 갱신은 `--force` 재생성이고, 그러면 **에디터에서 손으로 만진 값이 있으면 날아간다.** #149 이후 손댄 적이 없음을 전제한다 — 다르면 그 값을 스크립트 기본값으로 먼저 옮겨야 한다.

**유니티 빌드 섀도잉.** 새 `constexpr` 이름을 다른 파일과 겹치지 말 것(C4459). 이 설계의 이름은 전부 `Explosion*` 접두어다. Editor 빌드를 통과해도 Server 풀 유니티에서 깨진 전례가 있다.

**머티리얼 로드 실패는 조용하다.** `used_with_instanced_static_meshes` 가 없으면 `GetMaterial()` 은 정상을 반환하는데 화면은 기본 머티리얼이다(#97). 회색 구체가 뜨면 이것부터 본다.

## 8. 한계 (의도한 것)

**오버드로우가 늘어난다.** 반투명 층이 2 → 3 이고, 연기는 세 층 중 **가장 큰** 구체다(260uu). 픽셀 비용은 동시 개수에 선형으로 남고 이 작업은 그 기울기를 **키운다.**

#149 §9.1 이 동시 90 에서 `Translu` mean 0.18 / p99 0.54 (기준선 0.19 / 0.61) 로 여유를 확인했으므로 감당 가능할 것으로 보지만, **예측이 아니라 측정으로 확인한다**(§9). 무너지면 `re.Fx.ExplosionBudget` 이 그 축의 노브다 — 이 작업은 기본값 256 을 바꾸지 않고, 측정이 요구하면 그때 근거와 함께 내린다.

**드로우콜 상수값이 4 → 6 으로 오른다.** 상수성은 유지되지만 상수가 커진다. 층당 +2 는 #149 §9.1 실측이다.

**주황 그라데이션은 절반만 해결된다.** §2.2 — 색과 밝기가 진행도에 묶여 있는 구조는 그대로다.

## 9. 검증

| 게이트 | 기준 |
|---|---|
| 빌드 | `Project_REEditor` + `Project_REServer`(풀 유니티, `-DisableAdaptiveUnity`) 둘 다 `Result: Succeeded` |
| headless 프로브 | `ExplosionProbe` 로그가 나오고 `M_REExplosionSmoke 로드 실패` 가 **없어야** 한다 |
| 연출 (핵심) | 실 RHI 스크린샷 **4장**: 직선(`re.Debug.BossPattern` 기본) / 곡사(`re.Debug.BossPattern 2`) × 튜닝 전·후. 대조군 `ScreenShot00161`·`00162` 가 이미 디스크에 있다 |
| 드로우콜 | `scripts/profile.ps1 -Bullets 5000 -Frames 720 -ExtraExec "re.Fx.Explosions 1,re.Debug.FakeHitTargets 16,re.Fx.ExplosionBudget 0"` — `Draws` 가 #149 의 229 대비 **+2 수준**(≈231). 크게 벗어나면 연기가 인스턴스로 배칭되지 않은 것이다 |
| 오버드로우 | 같은 런의 `Translu` mean/p99 가 #149 (0.18 / 0.54) 대비 무너지지 않는지. 오르는 것은 예상대로고(§8), **얼마나** 오르는지를 기록한다 |

**연출 판정 기준** (스크린샷에서 눈으로):

1. 코어가 흰 덩어리가 아니라 **노랑-주황**으로 읽히는가
2. 폭발이 회색으로 열리지 않는가 (§4.4 램프가 먹었는가)
3. 연기 가장자리가 딱딱한 공 테두리가 아닌가 (§4.3 프레넬이 먹었는가)
4. 연기가 코어를 통째로 가리지 않는가 (§7 정렬)
5. 곡사 착지 폭발의 연기가 바닥에 묻히지 않는가

2·4 가 무너지면 폴백은 연기 `Opacity` 0.45 → 0.25. 3 이 무너지면 `Rim` 2.0 → 3.5. 판단이 서지 않으면 스크린샷을 사람에게 보여주고 묻는다.

### 9.1 측정 결과 (2026-09-13)

`scripts/profile.ps1 -Bullets 5000 -Frames 720`, 전 런 `re.Debug.FakeHitTargets 16`. 수치는
`scripts/profile-stats.ps1` 추출값(ms, `Draws`=`RHI/DrawCalls`, `Translu`=`Exclusive/RenderThread/RenderTranslucency`).

| 런 | 동시 폭발 | Draws mean | Draws p99 | Frame mean | RT mean | GPU mean | Translu mean | Translu p99 | Instances mean |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `d151_off` (첫 런, **폐기**) | 0 | 225 | 259 | 6.39 | 6.37 | 4.28 | 0.20 | 0.67 | 3,876 |
| `d151_nobudget` (`ExplosionBudget 0`) | 81~93 | 234 | 283 | 5.50 | 5.46 | 4.36 | 0.16 | 0.26 | 4,079 |
| `d151_budget256` (출하 설정) | 76~83 | 234 | 283 | 5.47 | 5.44 | 4.35 | 0.16 | 0.25 | 4,078 |
| `d151_off2` (기준선) | 0 | 228 | 277 | 5.46 | 5.43 | 4.26 | 0.16 | 0.24 | 3,857 |

**첫 기준선 런은 워밍업에 오염돼 폐기했다.** `d151_off` 는 3런 중 맨 처음 돌아 셰이더/PSO
컴파일을 뒤집어썼고, 그 결과 **폭발을 켠 런보다 느리게**(Frame 6.39 vs 5.50) 나왔다 —
그대로 뒀으면 "연기를 넣었더니 빨라졌다"는 헛소리를 적을 뻔했다. 같은 설정을 맨 끝에
다시 돌린 것이 `d151_off2` 이고, 아래 판정은 전부 이것과의 비교다. **프로파일 런 순서는
결과를 바꾼다 — 기준선을 먼저 돌리지 말 것.**

**드로우콜 — 예측대로 층당 +2, 개수와 무관.**

- 228 → 234, **정확히 +6**. 3층 × 2 다. #149 는 2층에서 +4 였으니 층당 상수 +2 가 그대로 재현됐다.
- p99 도 277 → 283 으로 같은 +6. 즉 최악 프레임에서도 개수에 비례하는 항이 없다.
- 동시 폭발이 76~93 사이에서 출렁이는 동안 `Draws` 는 234 고정이다. `ExplosionBudget` 을
  꺼도(81~93) 켜도(76~83) 같은 234 — **드로우콜은 동시 개수의 함수가 아니다.**
- 인스턴스는 3,857 → 4,079 로 +222 (≈74 폭발 × 3층). 층이 인스턴스로 배칭됐다는 직접 증거다.

**오버드로우 — §8 예측이 빗나갔다. 측정 한계 아래다.**

- `Translu` mean 0.16 → 0.16 으로 **변화 없음**. p99 만 0.24 → 0.25/0.26.
- GPU mean 4.26 → 4.35 (+0.09ms), Frame mean 5.46 → 5.47/5.50.
- §8 은 "가장 큰 반투명 구체가 하나 더 붙으니 오른다"고 예측했다. 실제로는 안 올랐다.
  이 씬에서 반투명 비용을 지배하는 것은 폭발이 아니라 탄환 4,000발 쪽이고, 폭발 90개가
  더해도 그 그늘에 묻힌다. `re.Fx.ExplosionBudget` 기본값 256 을 건드릴 근거가 이번 측정에는
  없다 — 세 런 모두 `버림=0` 으로 예산에 **한 번도 닿지 않았다.**

**연출 판정 — 초기값 그대로 통과.** 판정 1~4 를 실 RHI `-game` 화면에서 사람이 확인했고
전부 OK. 바꾼 머티리얼 파라미터 없음(`core-strength` 1.2 / `ring-strength` 3.0 /
`smoke-strength` 0.15 / `smoke-opacity` 0.45 / `smoke-ramp` 5.0 / `smoke-rim` 2.0 그대로).
5(곡사 착지)는 아래 하네스 한계 때문에 대조 촬영을 못 했다.

**§7 정렬 함정이 실제로 터졌다 — 판정 4 는 코드 수정 후에야 통과했다.**
연기 층을 넣은 순간부터 폭발 전체가 깜빡였다. 반투명은 프리미티브 단위로 정렬되고 기준이
컴포넌트 바운즈인데, 폭발 통 셋의 바운즈는 아레나 전역의 인스턴스를 다 감싸서 중심이 매
프레임 흔들린다 → 세 층의 상대 순서가 프레임마다 뒤집혔다. 연기는 코어를 통째로 감싸는 큰
구체라 앞에 오는 프레임에만 코어를 45% 알파로 덮고, 그 점멸이 화면 전체로 보였다.
코어·링만 있을 때 안 드러난 이유는 링이 바닥에 깔린 평면이라 순서가 뒤집혀도 가리는 면적이
거의 없었기 때문이다. `TranslucencySortPriority` 를 연기 1 / 링 2 / 코어 3 으로 못 박아
해결했다. **등록 순서는 정렬에 관여하지 않는다** — §5.2 의 "등록 순서가 화면에 남는다"는
서술은 틀렸다.

**하네스 한계 두 가지 (측정과 별개로 드러난 것).**

1. **`re.Debug.ScreenshotFrame` 이 탄환 렌더 프로세서 안에 있어서 곡사를 못 찍었다.**
   그 프로세서는 `FBulletTag` 쿼리를 들고 있어 Mass 탄환이 0 이면 런타임에 프루닝되고,
   Artillery 는 `FireArtillery()` 로 조기 리턴해 Mass 탄환을 만들지 않는다
   (`REBossCharacter.cpp:355`). 훅을 폭발 렌더 프로세서(쿼리 없음, `QueryBasedPruning=Never`)로
   옮겨 패턴과 무관하게 찍히게 고쳤다.
2. **틱 인덱스 스크린샷은 재현되지 않는다.** `ScreenshotFrame N` 은 프레임 수를 세는데
   프레임률이 런마다 크게 달라 같은 N 이 전혀 다른 게임 시각에 걸린다 — 실측으로 틱 400 은
   보스 후반 페이즈 로즈 패턴, 틱 401 은 초반 1페이즈였다. `-usefixedtimestep -fps=60` 을
   붙여도 두 런의 평균절대차가 41.3/255 로 남는다. **전/후 스크린샷을 나란히 놓는 §9 의
   연출 판정 방법은 성립하지 않는다.** 이번 판정은 대조군 없이 절대 기준으로만 했다.
   재현 가능한 전/후 비교가 필요하면 스크린샷 트리거를 게임 시간 기준으로 바꾸고 패턴 RNG
   시드를 고정해야 한다 — 후속 이슈 몫이다.

## 10. 범위 밖 (YAGNI)

- **코어 그라데이션 알파 리맵.** §2.2 의 구조적 원인. `Strength` 튜닝 후에도 스크린샷에 주황이 안 보이면 그때 `clamp(진행도 × ColorShift)` 를 lerp 알파에 끼운다 — 노드 2개다. 지금 하지 않는 이유는 (a) 가 "코드 0줄 파라미터 튜닝"으로 스코프돼 있고, 층이 3개가 되면 주황 대역을 연기 층이 대신 채울 수 있기 때문이다
- **4번째 층(스파크 / 잔불 / 열왜곡).** 3층으로 부족하다고 스크린샷이 말할 때만
- **연출 종류 분기(피격 / 착지).** 선행 설계 §10 — 별 이슈
- **NDC / SubUV 플립북.** 선행 설계 §4.2 기각. 실사 파티클 룩이 요구사항이 되면 그때 스파이크부터
- **`re.Fx.ExplosionBudget` 기본값 변경.** 측정이 요구하면 그때, 근거와 함께
- **`convert_explosion_fx.py` / `NS_REBulletExplosion` 제거.** 선행 설계 §10 과 같이 별 이슈
- **M7 프로파일 문서 재측정, README·포트폴리오 수치 갱신.** 선행 설계 §10
