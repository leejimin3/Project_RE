## 0. 한 줄 피치 (초안)

> UE5 Mass Entity 로 45,000 투사체를 60fps 에 유지하고, 데디케이티드 서버에서 N명이 같은 탄막을
> 보게 만든 탑뷰 탄막 보스전. 모든 아키텍처 선택은 실측으로 정당화했고,
> **측정 도구가 거짓말한 다섯 번을 문서로 남겼다.**

이 프로젝트가 주장하는 축은 두 개다. 게임 완성도가 아니다.

1. **대규모 투사체 시뮬레이션의 아키텍처 선택과 그 근거**
2. **서버 권위 하에서 수천 발을 복제 없이 동기화하는 설계**

세 번째 축이 하나 더 있고, 실제로는 이게 가장 희소하다.

3. **측정을 믿지 않는 태도** — 초록불이 거짓말한 사례와 그걸 잡은 방법

## 2. 소재 ① — Mass vs Actor, 아키텍처 선택을 숫자로 가름

**출처:** `docs/profiling/M3-mass-vs-actor.md`, `docs/profiling/M6-gpu-breakdown.md`

### 쓸 수 있는 수치 (M6 재측정 기준 — 이게 정본이다)

동일 5,000발, 1280×720, 720프레임 정상상태 캡처:

| | Mass (ISM) | Actor | 배수 |
|---|---:|---:|---:|
| GameThread mean | **4.03 ms** | **16.99 ms** | 4.2× |
| DrawCalls | **96** | **3,358** | 35× |
| Frame p99 | 8.80 ms | (게이트 미달) | — |

1,600발 (측정 당시 실제 게임플레이 부하):

| | Mass | Actor |
|---|---:|---:|
| GT | 3.24 ms | 7.54 ms |
| DrawCalls | 97 | 1,153 |
| Frame p99 | 6.93 ms | 12.00 ms |

### 스케일 곡선 — 이게 핵심 그림이다

```
탄환 수 →      100     1000     5000
Mass GT        2.71     3.17     4.03     ← 거의 평평
Actor GT       2.84     5.22    16.99     ← 선형 붕괴
```

**주장:** Mass 는 탄이 50배 늘어도 게임 스레드가 1.3ms 오른다. Actor 는 같은 구간에서 14.2ms 오른다.
Actor 5,000 은 프레임이 GT 에 완전히 묶인다(GT 16.99 ≈ Frame). Mass 5,000 은 GT 가 비어 있다.

### 프로세서 3분해 — 스레드 배치가 CSV 컬럼 이름에 박혀 있다

| CSV 컬럼 | 스레드 | mean | p99 |
|---|---|---:|---:|
| `REBullet/AllWorkers/BulletSim` | **워커** | 0.04 | 0.08 |
| `REBullet/GameThread/BulletRender` | 게임 | 0.74 | 1.33 |
| `REBullet/GameThread/BulletHit` | 게임 | 0.10 | 0.23 |

5,000발 부하에서 탄막 시뮬 총합이 **0.88 ms**. 이동은 워커 스레드로 완전히 빠졌다.

> **면접에서 물으면:** 왜 렌더 프로세서는 게임 스레드인가 →
> ISM 은 씬 컴포넌트라 트랜스폼 갱신이 게임 스레드 전용이다(`bRequiresGameThreadExecution=true`).
> 안 걸면 워커 스레드에서 크래시한다. 이 제약이 곧 남은 병목의 위치를 정한다.

### 최종 상한

| 항목 | 값 | 근거 |
|---|---|---|
| 60fps 투사체 상한 | **45,000** | `M6-gpu-breakdown.md` 부록 C |
| 상한 이력 | 30,000 → 50,000 (#95) → 45,000 (#98) | 부록 B, C |

상한이 **내려간 이력이 있다는 게 오히려 자산**이다. Niagara 플러그인을 켜면 폭발을 하나도
띄우지 않아도 게임 스레드가 +2.5ms 든다 — 되돌릴 수 있는 교환임을 알고 받아들인 것이다.

## 4. 소재 ③ — 데디 서버에서 수천 발을 복제 없이 맞추기

**출처:** `docs/guides/M5-정리.md`, `Core/REBossCharacter.cpp`, `Mass/REBulletSpawnSubsystem.cpp`

### 문제

Mass 엔티티는 복제되지 않는다. 그리고 **복제해서도 안 된다** — 수천 발이다.

### 설계

```
서버: 보스가 발사
      → Multicast RPC "패턴 P, 원점 O, 각도 A, 개수 N, 발사시각 T"
      → 서버 로컬 스폰 → 서버가 판정 (권위)
클라: RPC 수신 → 같은 파라미터로 로컬 스폰 → 클라가 그린다 (코스메틱)
```

**보내는 건 총알이 아니라 "총알을 만드는 법"이다.** 수천 발이 파라미터 몇 개로 압축된다.

### 설계 논점 세 개 — 여기가 서술할 값어치가 있는 부분

**① 왜 시드만으로는 안 되는가**
초안은 "시드 S 를 보내면 클라가 같은 난수로 재현"이었다. 부족했다.
시드가 결정하는 건 페이즈 로테이션 순서와 Artillery 모양 선택뿐이다. 반면
Fan 의 중심각과 Artillery 의 착지점은 **그 순간 플레이어 위치**에 달렸고,
플레이어 위치는 난수가 아니라 시드에서 유도할 수 없다.
→ 시드가 아니라 **계산된 발사 파라미터 자체**를 보낸다.

**② 왜 발사 시각을 같이 보내나**
클라는 RPC 를 늦게 받는다. 받은 순간 탄을 0 에서 시작하면 서버보다 뒤처진다.
`StartTime` 을 함께 보내면 클라는 "이 탄은 이미 0.08초 날아간 상태"로 스폰한다.

**③ 유도할 수 있는 건 안 보낸다**
탄 색 교차(`ShotParity`), 로브 위상, 링 회전 위상은 전부 `ServerTime` 에서 순수 유도한다.
카운터를 따로 두면 멀티캐스트 유실 시 클라마다 어긋난다.

```cpp
// REBossCharacter.cpp — 유실에 강한 파생
SP.ShotParity = (Interval > 0.f) ? (FMath::FloorToInt(ServerTime / Interval) & 1) : 0;
```

### 예외 경로도 서술할 가치가 있다

```cpp
// GetElapsedSince — 상·하한을 둘 다 막는 이유가 각각 다르다
return FMath::Clamp(GetServerNow() - ServerTime, 0.f, 1.f);
```

- **하한 0**: 접속 직후 GameState 복제 전이면 `GetServerWorldTimeSeconds()` 가 0 → 큰 음수
- **상한 1초**: 클라 시각이 EMA 수렴 중이거나 서버 재시작 직후면 큰 양수 →
  볼리 전체가 "이미 착지함"으로 스킵되어 **조용히 빈 화면**이 된다

### 판정을 클라에도 여는 설계 (#98/#102)

```cpp
ExecutionFlags = (int32)EProcessorExecutionFlags::AllNetModes;  // 판정은 양쪽
bRequiresGameThreadExecution = true;                            // TakeDamage 는 액터 호출
```

클라가 자기 시뮬로 탄을 지우고 폭발을 띄운다. **데미지만 `HasAuthority()` 가드로 서버에 남는다.**
복제 RPC 를 쓰지 않는 근거: 클라는 이미 `ServerTime` 으로 탄 위치를 자체 계산하므로 판정 근거가 있다.

## 6. 소재 ⑤ — 보스 패턴 15종과 패턴별 p99

**출처:** `docs/profiling/M7-pattern-p99.md`

수학 곡선을 탄막 지오메트리로 쓴다: 리사주, 장미(rose), 심장형(cardioid), 렘니스케이트,
초형식(superformula), 하이포트로코이드(스피로그래프), 3차 베지어 궤적.

**15종 전부 720프레임 p99 실측, 전부 60fps 게이트(16.6ms) 통과.**

| 최악 3종 | mean | p99 |
|---|---:|---:|
| LissajousStorm | 8.76 | **14.95** |
| BezierVortex | 10.53 | 13.40 |
| ArtilleryStorm | 8.75 | 12.92 |

### 임계 경로가 게임 스레드가 아니라 렌더 스레드다

곡사 패턴은 착지 폭발이 비용의 대부분이다. 하네스 기본값이 `re.Fx.Explosions 0` 이라
**끄고 재면 실물이 아니다** — 이걸 알아채고 `-ExtraExec` 로 덮은 게 M7 측정의 전제다.

### 서술할 만한 개별 설계

- **곡사 궤적 3차 베지어 승격**: 2차 제어점 C 를 `Start + (C-Start)·⅔` 로 차수 상승 →
  오프셋이 전부 0 이면 **기존 포물선과 대수적으로 같다.** 회귀 없이 궤적 성형을 추가한 방법
- **어긋내기(stagger)**: 볼리 하나가 한 프레임에 통째로 나가면 덩어리로 보인다.
  `Elapsed` 를 인덱스에 비례해 밀어 순차 발사처럼 보이게 한다. 단, 어긋냄이 비행의 79%를
  먹어 **탄이 착지점 근처에서 튀어나온** 실패를 겪고 돔에만 걸도록 좁혔다
- **MicroMissile 이 `ServerTime` 파생을 안 쓰는 이유**: 타이머가 ±5ms 흔들려
  `floor(ServerTime/Interval)` 이 인덱스를 건너뛴다(실측 104/98/103/97/105ms).
  방향 순환이 깨지므로 **볼리 카운터**를 페이로드로 보낸다

## 7. 소재 ⑥ — 클로즈드루프 스폰 컨트롤러 (제어 이론 적용)

**출처:** `Core/REBossCharacter.cpp::ResolveSpiralCount`, 이슈 #51/#88

측정 하네스가 "동시 탄환 5,000발 유지"를 요구하는데 오픈루프 스폰은 3,352발까지만 찼다.

### 적분 제어 + 안티와인드업 + 소수부 누산

```cpp
const float ShotsPerLife = BulletLifetimeSec() / FireIntervalSec();   // N = 데드타임
if (SpiralShotCount < FillShots)
{
    SpiralSpawnRate = FeedFwd;              // 채움 구간은 피드포워드만 (와인드업 방지)
}
else
{
    SpiralSpawnRate += Ki / (ShotsPerLife * ShotsPerLife) * (TargetLive - CurrentLive);
    SpiralSpawnRate = FMath::Clamp(SpiralSpawnRate, 0.f, (float)TargetLive);   // 안티와인드업 상한
}
SpiralSpawnAccum += SpiralSpawnRate;
Count = FMath::FloorToInt(SpiralSpawnAccum);
SpiralSpawnAccum -= Count;                  // 소수부 이월 — round() 면 매 발사 +20% 오버슛
```

### 게인 무차원화 — 이 항목의 핵심

1수명당 발사 수 `N = Lifetime/Interval` 은 이 루프의 **데드타임**이자
스폰율 → 라이브 카운트의 **정상상태 이득**(`live = rate · N`)이다.
그래서 원시 게인의 루프게인은 `N²` 에 비례한다.

**무차원화하지 않으면 설정을 바꾸는 순간 조용히 진동한다.**
실제로 그랬다 — `3.0/0.1`(N=30, 루프게인 3.6)에서 튜닝한 값이 `15.0/0.15`(N=100)로 바뀌며
루프게인 40 이 되어 **388~1,802 리밋사이클**에 빠졌고 프로파일 측정이 통째로 무의미해졌다(#88).

> **면접에서 물으면:** 왜 PID 가 아니라 I 만 썼나 →
> 목표가 정상상태 오차 0 이고 플랜트가 순수 적분기 + 데드타임이다. P 는 정상상태 오차를 남기고
> D 는 라이브 카운트 관측 노이즈(프레임 단위 소멸)를 증폭한다. 데드타임이 지배적이라
> 게인 마진이 좁고, 그래서 무차원화가 실제 문제였다.
