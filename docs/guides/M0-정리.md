# Milestone 0 정리 — 초심자용 해설

> **이 문서 목적**: M0에서 만든 코드를 언리얼 엔진을 처음 만지는 사람도 따라갈 수 있게 설명한다.
> 파일 경로와 함수 이름을 최대한 구체적으로 적었으니, 읽으면서 실제 파일을 같이 열어 보면 좋다.
>
> **엔진 버전**: UE 5.8 · **핵심 코드 위치**: `Source/Project_RE/Core/`, `Source/Project_RE/Mass/`

---

## 0. M0가 뭐였나

M0의 목표는 **게임을 만드는 게 아니라, 앞으로 게임을 얹을 "뼈대"와 "규칙"을 세우는 것**이었다.

이 프로젝트의 최종 목표는 *데디케이티드 서버 기반 협동 멀티플레이 탄막(bullet-hell) 게임*이다.
멀티플레이는 나중(M4~M5)에 붙이지만, **나중에 붙이기 쉽도록 지금부터 코드를 특정 규칙으로 쓰기 시작**하는 게 M0의 핵심이다.

M0는 GitHub 마일스톤 `M0: 셋업 + 아키텍처 결정`에 묶인 **5개 이슈**로 구성됐다.

| 이슈 | 제목 | 한 줄 요약 | 만든 것 |
|------|------|-----------|---------|
| #1 | 탑뷰 카메라 + PlayerController 뼈대 | 3인칭 템플릿을 위에서 내려다보는 쿼터뷰로 전환 | `RECharacterBase`, `REPlayerController` |
| #2 | MassEntity 플러그인 + Build.cs 모듈 | 수만 개 총알을 굴릴 ECS 엔진 켜기 | `Build.cs`, `REGameMode` 프로브 |
| #3 | 서버 권위 코드 패턴 확립 | "게임 상태 변경은 서버만" 규칙을 베이스 클래스에 박기 | `RECharacterBase`, `REPlayerController`, `REGameMode` |
| #4 | Mass Processor 시뮬/렌더 분리 | 계산(Sim)과 그리기(Render)를 별도 처리기로 쪼개기 | `REBulletSimProcessor`, `REBulletRenderProcessor` |
| #5 | 탄막 패턴 시드 RPC 인터페이스 설계 | "총알을 네트워크로 안 보내는" 구조의 진입점 만들기 | `REBossCharacter`, `EBulletPattern` |

> **중요**: M0의 코드는 대부분 **"스텁(stub, 뼈대)"** 이다. 실제 총알이 날아다니거나 이동하지 않는다.
> 클래스·함수·데이터 구조의 "빈 상자"를 정확한 위치에 만들어 두고, 로그로 "상자가 실제로 작동한다"는 것만 증명했다.
> 상자를 내용물로 채우는 건 M1부터다.

## 1. 파일 지도 (어디에 뭐가 있나)

```
Source/Project_RE/
├─ Project_RE.Build.cs        ← 이 모듈이 어떤 엔진 모듈에 의존하는지 (이슈 #2)
│
├─ Core/                      ← 게임플레이 액터(플레이어·보스·게임모드·컨트롤러)
│  ├─ RECharacterBase.h/.cpp  ← 플레이어 폰. 탑뷰 카메라 + HP(서버권위)  (#1, #3)
│  ├─ REPlayerController.h/.cpp← 우클릭 이동 입력 처리                     (#1, #3)
│  ├─ REGameMode.h/.cpp       ← 게임 규칙 컨테이너. BeginPlay에서 전부 실증 (#2, #4, #5)
│  └─ REBossCharacter.h/.cpp  ← 보스. 탄막 발사 진입점                   (#5)
│
└─ Mass/                      ← Mass(ECS)로 굴릴 총알 관련 데이터·처리기
   ├─ REBulletPattern.h       ← 탄막 패턴 종류 enum (Spiral/Fan/Homing)   (#5)
   ├─ REBulletFragments.h     ← 총알 한 개가 들고 다니는 데이터 조각       (#4)
   ├─ REBulletSimProcessor.h/.cpp    ← 총알 이동/수명 계산 (모든 곳 실행)  (#4)
   └─ REBulletRenderProcessor.h/.cpp ← 총알 그리기 (서버는 건너뜀)         (#4)
```

접두어 `RE`는 프로젝트 이름 **R**andom/**RE**(Project_RE)에서 온 클래스 접두어다.
언리얼은 클래스 이름 앞에 종류 문자를 붙이는 관습이 있다: 액터는 `A`, 언리얼 오브젝트는 `U`, 구조체는 `F`, enum은 `E`.
그래서 `ARECharacterBase`(A+RE), `UREBulletSimProcessor`(U+RE), `FBulletSimFragment`(F), `EBulletPattern`(E)처럼 읽힌다.

> **참고**: `Source/Project_RE/` 아래에는 `Project_RECharacter.cpp`, `Variant_Combat/`, `Variant_Platforming/` 같은
> 파일도 있다. 이건 언리얼 3인칭 템플릿이 원래 넣어준 **예제 코드**이고 M0에서 새로 만든 게 아니다.
> M0 결과물은 위 `Core/`, `Mass/` 두 폴더에 집중돼 있다.

## 2. 큰 그림 — 게임을 켜면 무슨 일이 일어나나

M0 코드가 실제로 도는 흐름은 딱 하나의 함수에서 시작한다:
**`AREGameMode::BeginPlay()`** (`Source/Project_RE/Core/REGameMode.cpp`).

게임모드(GameMode)는 언리얼에서 **"이 레벨의 규칙을 총괄하는 심판"** 같은 존재다.
`Config/DefaultEngine.ini`에 다음 줄이 있어서, 게임이 켜지면 이 게임모드가 자동으로 쓰인다:

```ini
GlobalDefaultGameMode=/Script/Project_RE.REGameMode
```

`BeginPlay()`는 레벨이 시작될 때 딱 한 번 호출되는 함수다. 여기서 M0의 4가지가 순서대로 실증된다:

```
게임 시작
  │
  ▼
AREGameMode 생성자           → 플레이어 폰 = ARECharacterBase, 컨트롤러 = AREPlayerController 지정
  │
  ▼
AREGameMode::BeginPlay()
  ├─ (1) MassEntitySubsystem 얻어서 테스트 엔티티 1개 생성       ← 이슈 #2 실증
  │        로그: "[RE] Mass entity created: Index=.. Serial=.."
  │
  ├─ (2) 두 Processor의 ExecutionFlags 값 로그로 출력           ← 이슈 #4 실증
  │        로그: "[RE] SimProcessor flags=7  RenderProcessor flags=5"
  │
  └─ (3) 보스(AREBossCharacter) 스폰 → TriggerBulletPattern() 호출 ← 이슈 #5 실증
           로그: "[RE] Boss::TriggerBulletPattern: .. -> spawned 16 entities"
```

동시에, 플레이어 쪽에서는:

```
플레이어 폰(ARECharacterBase)이 스폰되면
  → 생성자에서 탑뷰 카메라(SpringArm+Camera)가 세팅됨            ← 이슈 #1

컨트롤러(AREPlayerController)가 붙으면
  → BeginPlay에서 마우스 커서 표시 + 우클릭 입력 매핑            ← 이슈 #1
  → 우클릭하면 커서 아래 지점으로 폰이 걸어감
```

이제 이슈별로 하나씩, "왜 이렇게 썼는가"를 개념부터 파고든다.

## 3. 이슈 #1 — 탑뷰 카메라 + 우클릭 이동

**만든 파일**: `Core/RECharacterBase.h/.cpp`, `Core/REPlayerController.h/.cpp`

### 개념: 폰(Pawn)과 컨트롤러(Controller)

언리얼에서 "플레이어"는 두 조각으로 나뉜다:
- **Pawn/Character** = 월드에 실제로 서 있는 몸뚱이(메시, 콜리전, 카메라). 여기선 `ARECharacterBase`.
- **PlayerController** = 그 몸을 조종하는 "영혼". 입력을 받아 폰에게 명령한다. 여기선 `AREPlayerController`.

이 둘을 나누는 이유는, 나중에 멀티플레이에서 **"어느 컨트롤러가 어느 폰을 소유하는가"** 가 서버 권위의 핵심이 되기 때문이다.

### 탑뷰 카메라는 어떻게 만드나

핵심은 `ARECharacterBase` **생성자** (`RECharacterBase.cpp`)다. 카메라는 두 부품의 조합이다:

- **SpringArm(카메라 붐)** = 폰에서 뻗어 나온 낚싯대. 끝에 카메라를 매단다. 길이/각도를 정한다.
- **CameraComponent** = 실제 렌더링하는 눈.

`RECharacterBase.cpp` 생성자에서 세팅한 값:

```cpp
CameraBoom->TargetArmLength = 1500.f;                    // 폰에서 1500 유닛 떨어져서
CameraBoom->SetRelativeRotation(FRotator(-50.f, 0.f, 0.f)); // 아래로 50도 내려다봄 (쿼터뷰)
CameraBoom->bUsePawnControlRotation = false;             // 폰이 돌아도 카메라는 안 돌아감
CameraBoom->bInheritPitch = false;                       // (아래 세 줄: 카메라 각도를 절대 고정)
CameraBoom->bInheritYaw   = false;
CameraBoom->bInheritRoll  = false;
CameraBoom->bDoCollisionTest = false;                    // 벽에 카메라가 튕겨 들어오지 않게
TopDownCamera->SetFieldOfView(90.f);                     // 원근(90도 FOV) — 완전 직교는 아님
```

> **초심자 포인트**: `bInherit*`와 `bUsePawnControlRotation`을 `false`로 꺼야 카메라가 폰의 회전을 따라 흔들리지 않고
> "위에서 고정 각도로 내려다보는" LoL/이터널리턴 스타일이 된다. 이게 켜져 있으면 카메라가 캐릭터와 함께 빙빙 돈다.

또한 폰 자체가 컨트롤러 회전을 따라가지 않도록:
```cpp
bUseControllerRotationYaw = false;  // (Pitch/Roll도 동일)
GetCharacterMovement()->bOrientRotationToMovement = true; // 대신 "가는 방향"을 바라봄
```

### 우클릭 이동은 어떻게 작동하나

입력 처리는 `AREPlayerController`에 있다. 언리얼 5의 **Enhanced Input** 시스템을 쓴다.

보통은 에디터에서 `InputAction`, `InputMappingContext`를 에셋(uasset)으로 만든다.
하지만 여기서는 **코드로 직접 생성**했다 (`REPlayerController.cpp`의 `SetupInputComponent()`):

```cpp
ClickMoveAction = NewObject<UInputAction>(this, TEXT("IA_ClickMove"));
ClickMoveAction->ValueType = EInputActionValueType::Boolean;
TopDownMappingContext = NewObject<UInputMappingContext>(this, TEXT("IMC_TopDown"));
TopDownMappingContext->MapKey(ClickMoveAction, EKeys::RightMouseButton); // 우클릭 → 이 액션
```

> **왜 코드로?**: 에셋 없이 코드로만 만들면 파일 의존성이 없어 리뷰/재현이 쉽다. 다만 매 실행마다 새로 생성되는 임시(transient) 객체다.

이동의 실제 동작은 3개 함수로 나뉜다:

1. **`SetupInputComponent()`** — 우클릭을 `OnClickMove`에 연결. `BindAction(..., ETriggerEvent::Triggered, this, &AREPlayerController::OnClickMove)`
2. **`OnClickMove()`** — 우클릭 순간 실행. `GetHitResultUnderCursor()`로 커서 아래 월드 지점을 찾아 `MoveTarget`에 저장하고 `bMoveToTarget = true`.
3. **`PlayerTick()`** — 매 프레임 실행. `bMoveToTarget`이 켜져 있으면 폰을 `MoveTarget` 방향으로 조금씩 밀어냄(`AddMovementInput`). 목표 반경(`AcceptanceRadius = 120`) 안에 들어오면 멈춤.

> **M2 연결 지점**: `OnClickMove` 안에 이런 주석이 있다:
> `// TODO M2: 로컬 이동을 Server_RequestMove RPC + NavMesh 패스파인딩으로 교체`
> 지금은 평평한 바닥 위에서 직선으로 걸어가는 임시 버전이다. 진짜 길찾기(장애물 회피)는 M2에서 붙인다.

## 4. 이슈 #2 — MassEntity 켜기

**만든/수정한 파일**: `Project_RE.Build.cs`, `Core/REGameMode.cpp`(프로브)

### 왜 Mass인가

탄막 게임은 화면에 **총알이 수천~수만 개** 떠다닌다. 총알 하나하나를 언리얼 액터(Actor)로 만들면
액터마다 붙는 무거운 기능(Tick, 컴포넌트, 복제) 때문에 프레임이 무너진다.

그래서 **Mass**를 쓴다. Mass는 언리얼의 **ECS(Entity-Component-System)** 프레임워크다. ECS의 사고방식:
- **Entity(엔티티)** = 그냥 ID 번호 하나. 총알 한 발 = 엔티티 하나.
- **Fragment(프래그먼트)** = 그 엔티티가 들고 다니는 데이터 조각(위치, 속도 등). 언리얼 액터의 무거운 컴포넌트와 달리 순수 데이터.
- **Processor(프로세서)** = 같은 프래그먼트를 가진 엔티티 수만 개를 **한 번에 훑어서** 처리하는 로직.

수만 개를 개별 객체가 아니라 "데이터 배열 + 일괄 처리 루프"로 다루기 때문에 압도적으로 빠르다.

### Build.cs에서 한 일

`Project_RE.Build.cs`의 `PublicDependencyModuleNames`에 Mass 모듈 두 개를 추가했다:

```csharp
PublicDependencyModuleNames.AddRange(new string[] {
    "Core", "CoreUObject", "Engine", "InputCore", "EnhancedInput",
    ... ,
    "MassEntity",   // ← Mass ECS 코어
    "MassCore"      // ← Mass 공용 타입
});
```

`Build.cs`는 "이 모듈을 컴파일할 때 어떤 엔진 모듈을 링크할지"를 적는 C# 파일이다.
여기에 `MassEntity`를 추가해야 `UMassEntitySubsystem`, `FMassEntityManager` 같은 타입을 코드에서 쓸 수 있다.

> **⚠️ 확인 포인트 (초심자가 헷갈리기 쉬운 부분)**:
> 원래 이슈 #2는 `.uproject`에 MassEntity 플러그인을 명시적으로 켜라고 했다.
> 하지만 현재 `Project_RE.uproject`의 `Plugins` 목록에는 Mass 관련 항목이 **없다**(StateTree 3개만 있음).
> 그럼에도 빌드·실행이 되는 이유는, UE 5.8에서는 `Build.cs`의 모듈 의존성만으로 Mass 모듈이 링크되기 때문으로 보인다.
> 만약 나중에 "MassEntity를 찾을 수 없다"는 에러가 나면, `.uproject`에 플러그인을 명시적으로 켜는 것을 먼저 의심하라.

### 실증 프로브 (REGameMode.cpp)

`AREGameMode::BeginPlay()`에서 "Mass가 진짜 켜졌나"를 코드로 증명한다:

```cpp
if (UMassEntitySubsystem* Mass = GetWorld()->GetSubsystem<UMassEntitySubsystem>())
{
    FMassEntityManager& EM = Mass->GetMutableEntityManager();
    FMassArchetypeHandle Arch = EM.CreateArchetype({ FRETestFragment::StaticStruct() });
    FMassEntityHandle E = EM.CreateEntity(Arch);
    UE_LOG(LogTemp, Log, TEXT("[RE] Mass entity created: Index=%d Serial=%d"), E.Index, E.SerialNumber);
}
```

여기서 나오는 새 용어:
- **`UMassEntitySubsystem`** = 월드마다 하나 존재하는 Mass의 관리자. `GetWorld()->GetSubsystem<>()`으로 얻는다.
- **`FMassEntityManager`** = 실제로 엔티티를 만들고 지우는 객체. `GetMutableEntityManager()`로 접근.
- **Archetype(아키타입)** = "이 조합의 프래그먼트를 가진 엔티티들"의 틀. 먼저 아키타입(틀)을 만들고, 그 틀로 엔티티를 찍어낸다.
- **`FRETestFragment`** = M0 테스트 전용 껍데기 프래그먼트(`REGameMode.h`에 정의). `int32 Dummy` 하나만 있음. M1에서 진짜 총알 프래그먼트로 교체·삭제될 예정.

로그에 `[RE] Mass entity created`가 찍히면 Mass 서브시스템이 살아 있다는 증거다.

## 5. 이슈 #3 — 서버 권위 코드 패턴

**적용 파일**: `RECharacterBase.h/.cpp`, `REPlayerController.h/.cpp`, `REGameMode.cpp`

이 이슈는 새 기능이 아니라 **규칙**이다. 이 프로젝트의 가장 중요한 아키텍처 결정.

### 개념: 서버 권위(Server Authority)

멀티플레이에서 **누가 "진실"을 정하는가**의 문제다. 클라이언트(각 플레이어 PC)가 제멋대로
"내 HP는 만땅이야", "내가 널 맞췄어"라고 우기면 치트가 판친다.

그래서 원칙은: **게임 상태(HP, 위치, 점수 등)를 실제로 바꾸는 건 오직 서버만 한다.**
클라이언트는 "이거 해줘"라고 **요청**만 하고, 서버가 판단해 결과를 모두에게 **복제(replicate)**한다.

M4에서 데디케이티드 서버로 전환할 때 이 규칙을 미리 지켜 뒀으면 **"코드 재작성"이 아니라 "스위치 켜기"** 로 끝난다.
그래서 M0부터 베이스 클래스 3종에 이 패턴을 박아 뒀다.

### 규칙 1: 상태 변경은 `HasAuthority()` 가드 안에서만

`RECharacterBase.cpp`의 `TakeDamage()`가 교과서 예시다:

```cpp
float ARECharacterBase::TakeDamage(...)
{
    if (!HasAuthority())   // ← 서버가 아니면
    {
        return 0.f;        // ← 아무것도 안 하고 즉시 리턴
    }
    const float Applied = Super::TakeDamage(...);
    Health = FMath::Clamp(Health - Applied, 0.f, MaxHealth);  // ← 서버에서만 HP 차감
    return Applied;
}
```

`HasAuthority()`는 "지금 이 코드가 서버에서 돌고 있나?"를 묻는 함수다. `true`일 때만 HP를 건드린다.

### 규칙 2: 복제가 필요한 변수는 `Replicated`로 표시

`RECharacterBase.h`:
```cpp
UPROPERTY(Replicated, VisibleAnywhere, BlueprintReadOnly, Category = "Stats")
float Health = 100.f;
```

그리고 **어떤 변수를 복제할지 등록**하는 함수를 오버라이드해야 한다 (`RECharacterBase.cpp`):
```cpp
void ARECharacterBase::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);
    DOREPLIFETIME(ARECharacterBase, Health);   // ← Health를 복제 목록에 등록
}
```

이러면 서버가 `Health`를 바꿀 때마다 자동으로 모든 클라이언트에 값이 내려간다.

### 규칙 3: 클라이언트 입력은 `Server_` RPC로

`REPlayerController.h`에 서버 RPC "뼈대"가 있다:
```cpp
UFUNCTION(Server, Reliable)
void Server_RequestMove(FVector Target);
```

- **RPC(Remote Procedure Call)** = 한쪽(클라)에서 호출하면 다른 쪽(서버)에서 실행되는 함수.
- `UFUNCTION(Server, Reliable)` = "이건 클라가 호출하면 서버에서 돌아라, 반드시 도착 보장(Reliable)".
- 관습적으로 이름 앞에 `Server_`를 붙여 "이건 서버에서 실행됨"을 눈으로 알게 한다.

지금은 `Server_RequestMove_Implementation()`이 비어 있는 뼈대다(주석 `// TODO M2`). 실제 배선은 M2.

> **정리**: `TakeDamage`의 `HasAuthority()` 가드, `Health`의 `Replicated`, `Server_RequestMove` RPC —
> 이 3개가 "서버 권위 패턴"의 실물 견본이다. 앞으로 새 코드를 쓸 때 이 형태를 복사해서 따르면 된다.

> **`REGameMode`는 왜 가드가 없나?**: `REGameMode.h` 주석에 답이 있다 —
> *"GameModeBase는 서버에만 존재 → 모든 로직이 곧 서버 권위(별도 가드 불필요)."*
> 게임모드는 애초에 클라이언트에 존재하지 않으므로, 그 안의 코드는 자동으로 서버 전용이다.

## 6. 이슈 #4 — Processor를 시뮬/렌더로 분리

**만든 파일**: `Mass/REBulletFragments.h`, `Mass/REBulletSimProcessor.h/.cpp`, `Mass/REBulletRenderProcessor.h/.cpp`

### 개념: 왜 둘로 쪼개나

데디케이티드 서버에는 **화면이 없다**. 총알을 "그릴" 필요가 없다. 하지만 총알이 어디 있는지 **계산**은 해야 한다(피격 판정 등).
반대로 클라이언트는 계산도 하고 그리기도 한다.

그래서 총알을 다루는 로직을 두 개의 Processor로 나눴다:

| Processor | 역할 | 어디서 실행? | ExecutionFlags 값 |
|-----------|------|-------------|-------------------|
| `UREBulletSimProcessor` | 위치·속도·수명 **계산** | 싱글 + 서버 + 클라 **모두** | `AllNetModes` = **7** |
| `UREBulletRenderProcessor` | 화면에 **그리기**(ISM 트랜스폼) | 싱글 + 클라만 (**서버는 건너뜀**) | `Standalone \| Client` = **5** |

**`ExecutionFlags`** 는 "이 Processor가 어떤 네트워크 모드에서 돌아야 하나"를 정하는 값이다.
데디케이티드 서버로 전환하면, 엔진이 알아서 `RenderProcessor`(flag=5)를 **자동으로 건너뛴다**.
서버는 총알을 그리느라 CPU를 낭비하지 않는다. 이게 "서버 권위 분리"의 성능적 핵심이다.

### 코드에서 확인

`REBulletSimProcessor.cpp` 생성자:
```cpp
ExecutionFlags = (int32)EProcessorExecutionFlags::AllNetModes;   // 7: 어디서나 시뮬
```

`REBulletRenderProcessor.cpp` 생성자:
```cpp
// 5: 데디서버(Server) skip, 싱글/클라만 렌더
ExecutionFlags = (int32)(EProcessorExecutionFlags::Standalone | EProcessorExecutionFlags::Client);
```

### 프래그먼트: 총알이 들고 다니는 데이터

`REBulletFragments.h`에 두 개의 데이터 조각이 정의돼 있다:

```cpp
struct FBulletSimFragment : public FMassFragment   // 시뮬용 데이터
{
    FVector Velocity = FVector::ZeroVector;  // 속도
    float   Lifetime = 0.f;                  // 남은 수명
};

struct FBulletRenderFragment : public FMassFragment // 렌더용 데이터
{
    int32 InstanceIndex = INDEX_NONE;        // ISM 인스턴스 번호 (M1에서 사용)
};
```

### 쿼리: Processor가 "어떤 엔티티를 볼지" 정하기

각 Processor의 `ConfigureQueries()` 함수가 "나는 이런 프래그먼트를 가진 엔티티만 처리할 거야"를 선언한다.

`REBulletSimProcessor.cpp`:
```cpp
EntityQuery.AddRequirement<FBulletSimFragment>(EMassFragmentAccess::ReadWrite); // 시뮬 데이터만, 읽고 쓰기
```

`REBulletRenderProcessor.cpp`:
```cpp
EntityQuery.AddRequirement<FBulletSimFragment>(EMassFragmentAccess::ReadOnly);    // 위치는 읽기만
EntityQuery.AddRequirement<FBulletRenderFragment>(EMassFragmentAccess::ReadWrite);// 인스턴스는 쓰기
```

- **`ReadWrite` vs `ReadOnly`**: SimProcessor는 위치를 **바꾸므로** ReadWrite. RenderProcessor는 위치를 **참고만** 하므로 ReadOnly.
  이 접근 권한 선언 덕분에 Mass가 어떤 Processor들을 병렬로 돌려도 안전한지 자동 판단한다.

> **M0는 뼈대만**: 두 Processor의 `Execute()` 함수는 로그 한 줄만 찍는 스텁이다
> (`// M0: 구조만. 실제 이동/수명 계산은 M1.`). 실제 총알 이동 수학은 M1에서 채운다.

### 검증

`AREGameMode::BeginPlay()`가 두 Processor의 기본 객체(CDO)에서 flag 값을 읽어 로그로 출력한다:
```cpp
const uint8 SimFlags    = (uint8)GetDefault<UREBulletSimProcessor>()->GetExecutionFlags();
const uint8 RenderFlags = (uint8)GetDefault<UREBulletRenderProcessor>()->GetExecutionFlags();
UE_LOG(..., TEXT("[RE] SimProcessor flags=%d  RenderProcessor flags=%d"), SimFlags, RenderFlags);
```
로그에 `flags=7 ... flags=5`가 찍히면 분리 설정이 제대로 됐다는 증거다.

## 7. 이슈 #5 — 탄막 패턴 시드 RPC 인터페이스

**만든 파일**: `Mass/REBulletPattern.h`, `Core/REBossCharacter.h/.cpp`

### 개념: 총알을 네트워크로 보내지 않는다

가장 영리한 아키텍처 결정. 협동 멀티에서 총알 수만 개의 위치를 매 프레임 네트워크로 동기화하면 대역폭이 폭발한다.

대신 **결정론적 시뮬(deterministic simulation)** 을 쓴다:
> 서버는 총알을 보내는 대신 **(패턴 종류, 랜덤 시드, 시작 시각)** 딱 3개만 보낸다.
> 같은 시드를 받은 서버와 모든 클라이언트가 **각자 똑같은 계산**을 해서 똑같은 탄막을 그린다.

랜덤 시드가 같으면 랜덤 결과도 같으므로, 총알 하나 안 보내도 모두의 화면이 일치한다.

### 진입점: TriggerBulletPattern

`REBossCharacter.h`의 함수 시그니처가 그 계약(interface)이다:
```cpp
void TriggerBulletPattern(EBulletPattern Pattern, int32 Seed, float StartTime);
```
- `Pattern` — 어떤 탄막 모양인가 (`EBulletPattern` enum)
- `Seed` — 랜덤 시드. M5에서 서버→클라 동일 시드 시뮬에 쓸 값. **M0에서는 저장만 하고 미사용.**
- `StartTime` — 발사 시작 시각. 역시 M5용.

**`EBulletPattern`** (`REBulletPattern.h`)은 아직 슬롯만 있는 enum이다:
```cpp
enum class EBulletPattern : uint8 { Spiral, Fan, Homing };  // 나선 / 부채꼴 / 유도
```

### M0에서의 실제 동작 (싱글 경로)

`REBossCharacter.cpp`의 `TriggerBulletPattern()`은 M0에서 이렇게 한다:
1. `UMassEntitySubsystem`을 얻는다.
2. `FBulletSimFragment` + `FBulletRenderFragment`를 가진 아키타입을 만든다.
3. `switch(Pattern)`으로 패턴을 구분하지만, 각 case는 아직 `// TODO M1` 주석뿐 (실제 발사 수학 없음).
4. 패턴과 무관하게 **placeholder 엔티티 16개**(`BulletsPerPattern`)를 스폰한다. (속도 0, 수명 0 — 그냥 개수 실증용)
5. 로그: `[RE] Boss::TriggerBulletPattern: Pattern=0 Seed=12345 Start=0.00 -> spawned 16 entities`

### M5 전환 지점 (코드에 마킹됨)

`REBossCharacter.cpp` 함수 맨 위에 명시적 주석이 있다:
```cpp
// TODO M5: Multicast_TriggerPattern RPC로 교체 (서버→클라 시드 브로드캐스트, 총알 자체는 미전송).
//          현재는 싱글 로컬 직접 스폰 경로.
```
지금은 로컬에서 직접 스폰하지만, M5에서 이 자리를 **Multicast RPC**(서버가 모든 클라에게 시드를 뿌리는 호출)로 바꾸면
협동 멀티가 완성된다. **인터페이스는 그대로 두고 속만 바꾸는** 게 M0 설계의 목적이었다.

> **보스는 왜 `ARECharacterBase`를 안 물려받나?**: `REBossCharacter.h` 주석 —
> *"ARECharacterBase는 카메라 붐 달린 플레이어 폰이라 부적합."* 보스는 카메라가 필요 없으므로 `ACharacter`를 직접 상속했다.

| **결정론적 시뮬 + 시드** | 총알 대신 (패턴,시드,시각)만 보내 각자 동일 계산. |

## 10. M0 → M1 넘어가는 지점 요약

M0는 곳곳에 `// TODO M1` / `// TODO M2` / `// TODO M5` 주석으로 "여기를 채워라"를 남겼다. M1에서 손댈 곳:

| 위치 | M0 상태 | M1 할 일 |
|------|---------|---------|
| `REBossCharacter::TriggerBulletPattern` switch case | 빈 case | Spiral/Fan/Homing 발사 수학(각도→Velocity) 구현 |
| `REBulletSimProcessor::Execute` | 로그 스텁 | Velocity·Lifetime으로 실제 위치 이동/수명 감소 |
| `REBulletRenderProcessor::Execute` | 로그 스텁 | ISM 인스턴스 트랜스폼 갱신(실제 그리기) |
| `FBulletSimFragment` | Velocity/Lifetime 필드만 | 위치를 `FTransformFragment`로 확장 |
| `FRETestFragment` (REGameMode.h) | 테스트용 껍데기 | 삭제 또는 실제 총알 아키타입으로 교체 |

M0가 "빈 상자를 정확한 자리에 놓는" 단계였다면, M1은 그 상자를 "움직이는 탄막"으로 채우는 단계다.
```
