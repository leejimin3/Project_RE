## 0. M5가 뭐였나

M4까지로 게임은 **데디케이티드 서버에서 1명이** 돌아간다. 이동·대쉬·발사·HP가 원격 클라에서 정상 동작한다.

M5의 목표는 두 가지다:

1. **탄막을 클라 화면에 띄운다.** M4까지 데디 클라에는 탄이 하나도 안 보였다. HP만 깎였다.
2. **1명 전제를 걷어낸다.** 게임 루프 곳곳이 "플레이어는 1명"으로 하드코딩돼 있었다.

M5는 GitHub 마일스톤 `M5: 협동 멀티 (N명) + 시드 탄막 + 서버권위 피격`에 묶인 **이슈 7개**(닫힘 6, 백로그 1)와 **PR 7개**로 구성됐다.

| 이슈 | 제목 | 한 줄 요약 | 만든 것 |
|------|------|-----------|---------|
| #64 | 보스 탄막 패턴 다양화 | Spiral 하나만 쏘던 보스에 패턴 로테이션 | `AREBossCharacter` 페이즈 로테이션 |
| #67 | 보스 Homing 패턴 | **백로그로 분리 — 열린 채 마일스톤 종료** | (미구현) |
| #82 | 데디 2프로세스 검증 스크립트 | 손으로 하던 서버+클라 검증을 자동화 | `scripts/dedi-verify.ps1` |
| #84 | 보스 탄막 서버→클라 동기화 | 총알 대신 발사 파라미터를 보낸다 | `Multicast` RPC, `UREBulletSpawnSubsystem` |

## 2. 큰 그림 — 탄막이 클라 화면에 뜨기까지

M5 이전:

```
서버: 보스가 발사 → Mass 엔티티 스폰 → 서버가 판정
클라: (아무 일도 없음 — 화면이 비어 있다)
```

Mass 엔티티는 **복제되지 않는다.** 그리고 복제해서도 안 된다 — 수천 발이다.

M5 이후:

```
서버: 보스가 발사
      → Multicast RPC "패턴 P, 각도 A, 개수 N, 속도 V, 발사시각 T"
      → 서버 로컬 스폰 → 서버가 판정 (권위)
클라: RPC 수신 → 같은 파라미터로 로컬 스폰 → 클라가 그린다 (코스메틱)
```

**보내는 건 총알이 아니라 "총알을 만드는 법"이다.** 수천 발이 파라미터 몇 개로 압축된다.

### 왜 시드만으로는 안 되는가

설계 초안은 "시드 S를 보내면 클라가 같은 난수로 재현"이었다. 실제로는 부족하다.

시드가 결정하는 건 **페이즈 로테이션 순서**와 **Artillery 모양 선택**뿐이다. 반면:

- Fan 패턴의 **중심각**은 그 순간 플레이어 위치에 달렸다
- Artillery의 **착지점**도 마찬가지다

플레이어 위치는 난수가 아니다. **시드에서 유도할 수 없다.** 그래서 시드가 아니라 **계산된 발사 파라미터 자체**를 보낸다.

### 왜 발사 시각(T)을 같이 보내나

클라는 RPC를 늦게 받는다. 받은 순간 탄을 0에서 시작시키면 서버보다 뒤처진다.

`StartTime`을 함께 보내면 클라는 **"이 탄은 이미 0.08초 날아간 상태"** 로 스폰한다. 그래서 위치가 맞는다.

## 3. 이슈 #64 — 보스 탄막 패턴 다양화

### 왜 이게 M5의 선행 조건인가

M5는 "서버가 무엇을 보낼지"를 정하는 마일스톤이다. 그런데 패턴이 하나뿐이면 보낼 게 없다. **다양화를 먼저 해야 동기화가 실재하는 문제가 된다.**

### 페이즈 로테이션

`AREBossCharacter`가 시간 축으로 패턴을 바꾼다. 페이즈마다:

1. 다음 패턴을 뽑는다 (같은 패턴 2연속 금지)
2. 그 패턴의 발사 간격·페이즈 길이로 타이머를 건다
3. 페이즈가 끝나면 1번으로

```cpp
static const EBulletPattern Pool[3] = {
    EBulletPattern::Spiral, EBulletPattern::Fan, EBulletPattern::Artillery };
```

> **`Homing`은 풀에서 제외했다.** enum 슬롯은 있지만 미구현이다. 스폰 후 추적은 Mass 프래그먼트·프로세서 확장이 필요해 성격이 다른 작업이고, 백로그 이슈(#67)로 분리해 **닫지 않고 열어둔 채** 마일스톤을 끝냈다.

### 후속 수정 (PR #69)

초기 구현은 **고정 순서 순환**이었다. 그래서 Artillery가 항상 같은 자리에 왔다. 완전 랜덤 + 2연속 금지 + 등장 보장으로 고쳤다.

## 4. 이슈 #82 — 데디 2프로세스 검증 스크립트

### 개념: 왜 데디 검증이 손으로 하기 어려운가

데디케이티드 서버 테스트는 **프로세스가 2개 이상**이다. 서버 exe 하나, 클라 하나(또는 둘). 각각 로그가 따로 나오고, 둘을 **대조**해야 판정이 된다.

손으로 하면 매번 이렇다:

1. 서버 exe 기동
2. 15초 대기 (리스닝까지)
3. 클라 접속
4. 40초 대기 (프로브 완주)
5. 둘 다 종료
6. 두 로그 눈으로 대조

### 자동화한 판정 항목

`scripts/dedi-verify.ps1`이 검사하는 것:

| 어디 | 무엇 | 왜 |
|---|---|---|
| 서버 | `IpNetDriver listening` | 서버가 떴는가 |
| 서버 | `[Dash] dist=` 값이 기대 범위 | 판정·권위는 서버에 있어야 |
| 클라 | `[Attack] fire montage len=` | 코스메틱은 클라에 있어야 |
| **서버** | 코스메틱 로그가 **없을 것** | 데디 생략 가드가 뚫렸는지 |
| 양쪽 | `Assertion failed` 없을 것 | 크래시 |

**"있으면 안 되는 것"을 검사하는 항목이 있다는 게 중요하다.** 서버에 발사 몽타주 로그가 찍히면, 데디에 화면이 없는데 애니메이션을 재생하고 있다는 뜻이다.

### 접속 종료 후 구간 절단

서버가 먼저 내려가면 클라가 **로컬 월드로 폴백**한다. 그러면 클라 로그에 `role=ROLE_Authority` 줄이 찍히기 시작한다 — 실제 접속 중에는 절대 나오면 안 되는 값이다.

그래서 판정 전에 **접속 유지 구간만 잘라낸다.** 안 그러면 폴백 구간이 판정을 오염시킨다.

## 5. 이슈 #84 — 보스 탄막 서버→클라 동기화

### 개념: Multicast RPC

RPC는 세 종류다:

| 종류 | 누가 호출 | 어디서 실행 |
|---|---|---|
| `Server_` | 클라 | 서버 |
| `Client_` | 서버 | 그 클라 1명 |
| `Multicast_` | 서버 | **전원 (서버 + 모든 클라)** |

탄막 발사는 **전원이 같은 것을 봐야** 하므로 Multicast다.

### 서버·클라 공용 스폰 진입점

`UREBulletSpawnSubsystem`이 스폰을 한 곳으로 모은다. 서버든 클라든 같은 함수를 부른다.

**이게 중요한 이유**: 스폰 코드가 두 벌이면 미세하게 갈라지고, 그러면 서버와 클라가 다른 탄막을 그린다. **한 벌로 유지하는 것이 동기화의 전제다.**

`REBulletPatternGenerator`가 **무상태 순수 함수**인 것도 같은 이유다. 내부 상태가 없으면 같은 입력에 항상 같은 출력이 나온다.

### 렌더는 이미 준비돼 있었다

```cpp
// REBulletRenderSubsystem
if (InWorld.GetNetMode() == NM_DedicatedServer) { return; }
```

**서버는 안 그리고 클라는 그린다.** M0/M1에서 넣어둔 이 가드 덕에, 클라 월드에 엔티티만 생기면 렌더는 자동으로 붙었다.

## 6. 이슈 #85 — N인 접속 대응

### 찾아낸 단일 플레이어 가정 3곳

| 위치 | 무엇이 문제 | 증상 |
|---|---|---|
| `AREGameMode::EndGame` | 첫 PC 하나에만 결과 전송 | **2번 플레이어는 결과 화면이 안 뜬다** |
| `AREBossCharacter` Fan 중심각 | 첫 플레이어 방향 고정 | 보스가 2번을 조준하지 않는다 |
| `AREBossCharacter` Artillery 착지점 | 첫 플레이어 위치 고정 | 위와 같음 |

**전부 크래시가 아니라 무반응이다.** 에러 로그 하나 없다. 그래서 눈치채기 어렵다.

### 정한 규칙

| 항목 | 결정 |
|---|---|
| 보스 타깃 | 전 플레이어 대상 (조준 패턴은 최근접 등 정책 적용) |
| 승패 | **전원 사망 = 패배.** 1명 사망은 관전 |
| 결과 전파 | 전 PC 순회 |
| 리스폰 | 없음 (M2에서 스코프 아웃) |

> **승패 규칙을 "전원 사망"으로 정한 이유**: 1명 죽어서 게임이 끝나면 협동이 성립하지 않는다. 남은 사람이 계속 싸울 수 있어야 한다.

## 7. 이슈 #86 — N인 서버권위 피격

### 문제: 플레이어 0번만 검사

```cpp
// M5 이전 — REBulletHitProcessor.cpp
APawn* Pawn = UGameplayStatics::GetPlayerPawn(World, 0);
```

**2번 이후 플레이어는 탄에 맞아도 아무 일이 없다. 영구 무적이다.**

같은 구조가 `REBulletHitProcessor`(직선탄)와 `REArcHitProcessor`(곡사탄) **두 곳에 verbatim으로 복사**돼 있었다.

### 더 고약한 것: 대쉬 무적이 전역이었다

대쉬 무적 태그 검사도 그 1명 기준이었다. 그래서:

**2번 플레이어가 대쉬하면 1번이 무적이 된다.**

### 해결: 대상 수집을 공용 함수로

`REHitTargets.h` / `.cpp` 신설:

```cpp
struct FREHitTarget
{
    ARECharacterBase* Player;
    FVector           Location;
};

void GatherHitTargets(const UWorld* World, TArray<FREHitTarget>& Out);
```

- `Execute` 진입 시 **1회** 수집 → 청크 루프 안에서 N회 비교
- 대쉬 무적은 **개별화** — 대쉬 중인 본인만 목록에서 빠진다
- 두 프로세서가 같은 함수를 쓴다 → **한쪽만 고치는 사고가 구조적으로 불가능해진다**

> **M6에서 이 계약이 뒤집힌다.** "목록에서 빼면 거리 비교 자체가 없다"는 건 **탄환도 소멸하지 않는다**는 뜻인데, 그게 나중에 "대쉬로 통과하면 탄이 사라져야 한다"는 요구와 충돌한다. → M6 Issue #102

### 한 프레임 지연 (의도적)

`Execute` 진입 시 1회만 스냅샷하므로, **같은 틱 안에서 앞선 탄에 죽은 플레이어는 뒤따르는 탄에는 여전히 살아 있는 대상으로 보인다.** 시체가 그 틱 동안 탄을 흡수한다.

의도적으로 남겼다. 매 탄마다 재수집하면 비용이 폭증하고, 한 틱 오차는 게임플레이에 보이지 않는다.

## 8. 이슈 #87 — dedi-verify N인 판정

### 문제: 반쪽 판정인데 초록불

`-Clients 2`로 돌리면 판정이 반쪽인데 **전 항목 PASS**가 났다.

원인:

```cpp
// REPlayerController — 프로브 완주 직후
FPlatformMisc::RequestExit(false);
```

서버측 헤드리스 프로브는 **클라가 접속할 때마다 그 클라의 서버측 PC에서** 돈다. 그런데 완주하면 **프로세스를 스스로 종료**한다.

**먼저 붙은 클라의 프로브가 끝나는 순간 서버가 내려간다.** 뒤 클라의 프로브는 시작도 못 한다.

그런데 판정은 통과한다 — 뒤 클라의 **코스메틱 로그는 접속 직후에 이미 찍혔기** 때문이다.

### 해결

1. **종료 결정을 GameMode로 옮긴다.** 각 PC는 자기 프로브만 알므로, 완주 카운트는 전체를 아는 쪽이 세야 한다
2. **판정을 클라 수만큼 센다.** 존재 여부가 아니라 개수

```
[PASS] server: 프로브 완주 (2건)      ← 기대 2건
[FAIL] server: 프로브 완주 — 1건, 기대 2건
```

> **이 이슈가 세운 원칙**: 검증 도구에서 가장 나쁜 실패는 실패를 못 잡는 게 아니라, **못 잡으면서 초록불을 내는 것**이다. M6에서 같은 부류가 두 번 더 나온다(#103, #112).

## 9. 핵심 용어집 (한 줄 요약)

| 용어 | 뜻 |
|---|---|
| **데디케이티드 서버** | 화면 없이 판정만 하는 서버 프로세스. 리슨 서버(호스트=서버)와 대비 |
| **Multicast RPC** | 서버가 호출하면 서버+전 클라에서 실행되는 원격 호출 |
| **권위(Authority)** | 그 값을 결정할 자격. `HasAuthority()`가 true면 서버 |
| **코스메틱** | 판정에 영향 없는 표현(애니메이션·이펙트). 클라에만 있으면 된다 |
| **`ROLE_AutonomousProxy`** | 내가 조종하는 폰의 원격 역할. 서버에서 본 원격 클라 폰이 이 값 |
| **`ROLE_SimulatedProxy`** | 남이 조종하는 폰. 복제된 위치를 따라가기만 한다 |
| **헤드리스 프로브** | `-unattended`로 켜지는 자동 조작. 사람 없이 이동·발사·대쉬를 수행해 로그를 남긴다 |
| **폴백 구간** | 서버 접속이 끊긴 뒤 클라가 로컬 월드로 돌아간 구간. 판정에서 잘라내야 한다 |

## 10. 직접 확인하는 법

### 자동 검증 (권장)

```powershell
scripts/dedi-verify.ps1            # 클라 1명
scripts/dedi-verify.ps1 -Clients 2 # 클라 2명
scripts/dedi-verify.ps1 -SelfTest  # 판정 로직만 검사 (프로세스 미기동)
```

`-SelfTest`는 합성 로그로 **판정 자체가 고장을 잡는지** 확인한다. 정상 로그는 통과하고, 일부러 망가뜨린 로그는 실패해야 한다.

### 손으로 띄워 보기

```powershell
# 서버
Saved\StagedBuilds\WindowsServer\Project_RE\Binaries\Win64\Project_REServer.exe `
  -log -port=7777 -ExecCmds="re.Coop.ExpectedPlayers 2"

# 클라 (2번 실행)
UnrealEditor.exe Project_RE.uproject 127.0.0.1:7777 -game -windowed -ResX=1280 -ResY=720 -log
```

> `re.Coop.ExpectedPlayers 2`가 **필수**다. 서버는 지정 인원이 전부 준비될 때까지 보스 발사를 시작하지 않는다.
>
> `-unattended`는 넣지 마라 — 헤드리스 프로브가 켜져 자동 조작 후 4초 만에 스스로 종료한다.

### 무엇을 보면 M5가 됐다고 할 수 있나

- 클라 화면에 **탄막이 보인다** (M4까지는 안 보였다)
- 두 클라가 **같은 탄막**을 본다
- 2번 플레이어도 **탄에 맞는다**
- 2번 플레이어가 죽어도 **1번은 계속 싸운다**, 전원 죽으면 둘 다 결과 화면
- 1번이 대쉬해도 **2번은 무적이 아니다**

## 11. M5 → M6 넘어가는 지점

| 위치 | M5 상태 | M6에서 한 일 |
|---|---|---|
| `EBulletPattern::Homing` | 미구현, 백로그 분리 | 그대로 (열린 채) |
| `GatherHitTargets` 대쉬 처리 | 목록에서 제외 = 탄도 안 사라짐 | `bInvulnerable` 표시로 변경, 탄은 소멸 (#102) |
| 탄환 머티리얼 | 흰 구슬, 겹치면 선으로 보임 | 색 교차 + 언릿 발광 (#97) |
| 탄환 소멸 | 소리 없이 사라짐 | Niagara 폭발 (#98) |
| `dedi-verify` | 스테이징 신선도 미검사 | 낡은 서버 거짓 통과 차단 (#103) |
| `dedi-verify` | 이동 거리 미검사 | `Assert-Progress` 추가 (#112) |
| 데디 우클릭 이동 | **1/10 속도로 동작 (미발견)** | 이동목표 복제 + 클라 예측 (#112) |
