# Milestone 6 정리 — 초심자용 해설

> **이 문서 목적**: M6에서 만든 코드와 **잰 수치**를 따라갈 수 있게 설명한다. M6는 기능보다 측정이 많은 마일스톤이라, "무엇을 만들었나"만큼 "무엇을 어떻게 쟀나"가 중요하다.

## 0. M6가 뭐였나

M5까지로 게임은 돈다. 데디 서버에서 N명이 같은 탄막을 보고, 각자 맞고, 각자 죽는다.

**그런데 보여줄 수가 없다.** 탄이 흰 구슬이라 겹치면 선으로 보이고, 맞아도 소리 없이 사라지고, 화면에 내 HP조차 없다.

M6의 목표는 **"남에게 보여줄 수 있는 상태"** 다. 포트폴리오 첫 장에 "N개의 투사체를 띄우는" 이라고 쓰려면 그 N이 커야 하고, 화면이 그 주장을 스스로 증명해야 한다.

M6는 GitHub 마일스톤 `M6: Niagara 렌더 + UI 폴리시 + 최종 영상`에 묶인 **이슈 13개**(닫힘 12, 열림 1)와 **PR 11개**로 구성됐다.

## 2. 큰 그림 — 이 마일스톤은 수치로 굴러간다

M6의 거의 모든 판단이 **잰 값** 위에 서 있다. 그래서 순서가 이렇다:

```
#88 측정 도구 복구
  ↓
#50 병목 진단 → "GPU 아님, 고칠 것 없음"
  ↓
#95 그림자 제거 → 상한 30,000 → 50,000
  ↓
#97 머티리얼 (시각) → 스크린샷 검증 수단을 먼저 만듦
  ↓
#98 폭발 → Niagara 고정비로 상한 50,000 → 45,000 (교환)
  ↓
#102/#106/#107 게임플레이 결함 3건 (연쇄로 발견)
  ↓
#100 HUD
  ↓
#112 데디 이동 (직접 플레이해서 발견)
```

### 최종 수치

| 항목 | 값 | 근거 |
|---|---|---|
| 60fps 투사체 상한 | **45,000** | 부록 C |
| 상한 이력 | 30,000 → 50,000(#95) → 45,000(#98) | 부록 B, C |
| 그림자 제거 효과 | GPU 17.16ms → 6.13ms (40,000발) | 부록 B |
| Niagara 플러그인 고정비 | 게임 스레드 **+2.5ms** | 부록 C |
| 동시 폭발 스폰 안전선 | **200** (무너지지 않음) | 부록 C.7 |

## 3. 이슈 #88 — 프로파일링 하네스 복구

측정하려니 측정 도구가 안 돌았다. 세 가지가 겹쳐 있었다.

### (1) CSV가 안 나온다

엔진 CSV 프로파일러의 출력 경로가 **엔진 빌드 종류에 따라 갈린다.**

- 런처 바이너리 빌드 → `%LOCALAPPDATA%` 엔진 유저 디렉터리
- 소스 빌드 → 엔진 트리 자신의 `Engine/Saved`

한 곳만 보면 정상 기록됐는데도 "안 나옴"으로 오진한다. **세 곳 다 훑도록** 고쳤다.

### (2) 캡처 창의 대부분이 빈 씬

부팅 시점부터 캡처하면 보스가 아직 안 쏜다. 실측 17.9초 창 중 **13.3초가 발사 전**이었다.

```powershell
-csvStartOnEvent=REBulletsFilled     # 탄환을 다 채운 순간부터 캡처
-csvCaptureOnEventFrameCount=720
```

### (3) 스폰 컨트롤러가 진동한다

목표 탄환 수를 맞추는 적분 컨트롤러가 400~1800발 사이로 흔들렸다.

원인은 **루프게인이 설정값에 따라 달라지는 것**이었다. 탄 수명과 발사 간격이 바뀌면 실효 게인이 같이 변한다.

```
G = N² · Ki      (N = 수명 / 발사간격)
```

게인을 **무차원화**해서 설정과 무관하게 만들었다.

> **왜 이걸 먼저 고쳤나**: 측정 도구가 조용히 틀린 값을 주면 그 위에 쌓는 모든 판단이 틀린다. M6의 나머지가 전부 수치 위에 선다.

## 4. 이슈 #50 — 병목 진단, 그리고 "고치지 않기"

Mass 5000발에서 GPU가 병목이라는 가설이 있었다. Niagara 전면 교체라는 수 주짜리 작업의 근거였다.

**측정 결과 병목이 없었다.** 코드 변경 없이 문서만 남기고 닫았다.

> **"고치지 않기로 한 것"도 산출물이다.** 이 판정이 없었으면 근거 없이 큰 작업을 시작했을 것이다.
>
> 나중에 #98에서 Niagara를 켜긴 하는데, 그건 **렌더 교체가 아니라 이펙트 추가**라 성격이 다르다.

## 5. 이슈 #95 — 그림자 제거

### 무엇을 껐나

```cpp
// REBulletRenderSubsystem
ISM->SetCastShadow(false);
ISM->bAffectDynamicIndirectLighting = false;
ISM->bAffectDistanceFieldLighting = false;
```

### 왜 이렇게 큰 효과가 나나

탄막에서 **탄환 그림자는 시각 기여가 사실상 없다.** 탄은 작고 빠르고 수천 개다. 그런데 그림자는 그 수천 개를 전부 다시 그린다.

| 40,000발 | GPU |
|---|---|
| 그림자 켬 | 17.16ms |
| 그림자 끔 | **6.13ms** |

Lumen(간접광)도 같은 이유로 뺐다. 움직이는 인스턴스 수천 개가 서피스 캐시를 매 프레임 무효화해서, **카메라가 탄막을 담을 때마다 GPU가 수십 ms 튀었다.**

**병목이 GPU에서 게임 스레드로 넘어갔다.** 60fps 상한: 30,000 → **50,000.**

## 6. 이슈 #97 — 탄막 머티리얼

### 문제: 여러 발이 겹치면 선으로 보인다

각각이 독립된 투사체로 읽혀야 하는데 덩어리로 보였다.

### 먼저 만든 것: 스크린샷 CVar

```
re.Debug.ScreenshotFrame N    # 렌더 프로세서 N번째 실행에서 PNG 저장
```

**시각 결과는 수치 게이트로 판정할 수 없다.** 매번 사람이 눈으로 봐야 하고, 그 왕복이 렌더 작업의 실제 병목이었다. 그래서 검증 수단을 먼저 만들고 그 위에서 반복했다.

### 그 CVar가 없었으면 못 찾았을 버그

**머티리얼이 조용히 기본 머티리얼로 폴백하고 있었다.**

원인은 `bUsedWithInstancedStaticMeshes` 플래그 누락이다. ISM에 쓰려면 머티리얼에 이 용도 플래그가 있어야 하는데, 없으면 **엔진이 조용히 기본 머티리얼로 대체**한다.

**`GetMaterial(0)`은 정상적으로 내가 만든 머티리얼을 돌려준다.** 그래서 코드로는 절대 안 잡힌다. 화면을 봐야만 보인다.

### 설계도 틀렸다

처음 진단은 "경계가 안 보이는 건 셰이딩 문제"였다. 프레넬 림(가장자리 강조)을 넣었더니 **오히려 더 뭉쳤다.**

원인은 기하학적이었다:

```
탄 간격 30uu  <  탄 지름 50uu   → 물리적으로 겹쳐 있다
```

셰이딩으로 풀 수 있는 문제가 아니었다. 최종 해법은 **인접 탄 색 교차(체커보드)** 다 — 퍼인스턴스 커스텀데이터로 인접한 탄에 다른 색을 준다.

### 퍼인스턴스 커스텀데이터

ISM은 인스턴스마다 float 값을 몇 개 실어 보낼 수 있다. 머티리얼이 그걸 읽는다.

```
[0] = 스폰 팝 (막 생긴 탄을 잠깐 크게)
[1] = 색 선택 (0=빨강, 1=파랑)
```

## 7. 이슈 #98 — 탄환 소멸 폭발

### 교환: 상한 50,000 → 45,000

**Niagara 플러그인을 켠 것만으로 게임 스레드가 +2.5ms 든다. 폭발을 하나도 안 띄워도 그렇다.**

| 50,000발 | Frame p99 |
|---|---|
| #98 이전 | 15.18ms |
| 폭발 끈 상태 (3회 반복) | 17.52 / 17.97 / 17.61 |

세 번 다 일관되게 나빠졌다 — 런간 노이즈(±3%)의 8배다.

| 탄환 | Frame p99 | 판정 |
|---|---|---|
| 40,000 | 14.95 | 여유 |
| **45,000** | **16.53** | **새 상한** |
| 50,000 | 17.52 | 초과 |

**되돌릴 수 있는 교환이다.** Niagara 플러그인을 끄면 상한이 복귀한다.

### 판정을 클라에 개방한 이유

곡사탄이 수천 개가 될 경우, 폭발 하나하나를 서버가 Multicast로 알리면 **그 자체가 병목**이 된다.

그래서 **소멸 판정은 클라가 로컬로 하고, 데미지만 서버가 정한다.**

```cpp
if (T.Player->HasAuthority())        // 데미지 = 서버 권위
{
    T.Player->TakeDamage(...);
}
REExplosionFx::SpawnBulletExplosion(World, BulletLoc);  // 폭발 = 클라도
Ctx.Defer().DestroyEntity(...);                          // 소멸 = 클라도
```

### 🔴 곡사탄 폭발이 한 번도 안 떴다 (검증에서 잡음)

`UREArcFxProcessor`를 시뮬보다 **먼저** 돌게 등록했다. 의도는 "시뮬이 파괴하기 전에 위치를 읽는다"였다.

**그런데 `Elapsed`를 증가시키는 게 바로 그 시뮬이다.**

- 착지 프레임: FX가 먼저 돌아 **아직 갱신 전** `Elapsed`(< `FlightTime`)를 본다 → 조건 거짓
- 다음 프레임: 엔티티가 이미 파괴됐다 → 볼 대상이 없다

**조건이 영원히 거짓이다.** 크래시도 에러 로그도 없다.

잡은 신호:

| | 폭발 총합 | 직선탄 피격 | 곡사탄 초과분 |
|---|---|---|---|
| 수정 전 (착지점 12) | 66 | 66 | **0** |
| 수정 전 (착지점 200) | 73 | 73 | **0** |
| 수정 후 (착지점 12) | 138 | 79 | **59** |

**착지점을 16배로 늘려도 폭발 수가 안 움직이는 게 결정타였다.**

`ExecuteAfter`로 고쳤다. 뒤에 돌아도 안전하다 — 시뮬의 파괴는 `Defer()`라 **페이즈 끝에야 반영**되므로 트랜스폼을 그대로 읽을 수 있다.

## 8. 이슈 #103 — 낡은 서버로 검증하고 PASS

서버 판정 로직을 바꾸고 검증을 돌려 **16항목 전부 PASS**를 받았다. 그런데 로그 형식이 방금 넣은 것과 달랐다.

```
staged exe:  Aug 14 01:57
source    :  Aug 15 23:30
```

**서버 exe가 하루 반 낡아 있었다.**

### 왜 서버만 낡나

| | 어디서 뜨나 | 최신인가 |
|---|---|---|
| 클라 | 방금 빌드한 에디터 바이너리 | ✅ |
| **서버** | **스테이징 산출물(쿡 필요)** | ❌ |

`Build.bat`으로 컴파일해도 **스테이징된 exe는 안 바뀐다.** 재쿡·재스테이징이 별도 단계다.

### 해결: 매번 재쿡하지 않고, 거짓 통과만 막는다

쿡은 수 분~수십 분이라 매번 하면 검증 리듬이 깨진다. 그래서:

**서버 exe의 수정 시각이 `Source/`의 최신보다 오래됐으면 실패시킨다.**

```
스테이징 서버가 소스보다 낡았다 — 서버 코드 변경이 검증되지 않는다 (#103).
  staged: 2026-08-15 23:38
  source: 2026-08-16 01:53   (REBossCharacter.h)

  재스테이징:
    RunUAT.bat BuildCookRun -project=... -server -noclient -cook -stage -pak -build

  렌더/클라 전용 변경이라 서버가 무관하면: -SkipStaleCheck
```

### 언제 재스테이징이 필요한가

| 무엇을 고쳤나 | 재스테이징 |
|---|---|
| 서버 코드 (Mass 판정, `TakeDamage`, GameMode, RPC) | **필요** |
| `Config/*.ini` | **필요** (pak 안에 들어간다) |
| 클라 전용 (렌더, FX, UI, 머티리얼) | 불필요 |

> **mtime 기반이라 오탐이 난다.** `git checkout` / `git stash pop`은 내용이 같아도 수정 시각을 갱신한다. **안전한 방향의 오탐**이다 — 통과를 막지, 거짓 통과를 만들지 않는다.

## 9. 이슈 #102 — 대쉬 통과 시 탄환 소멸

### M5 계약을 뒤집는다

M5에서 대쉬 무적을 개별화하면서 **"대쉬 중인 본인만 목록에서 빠진다"** 로 확정했다. 목록에서 빠지면 거리 비교 자체가 없으므로 **탄환도 소멸하지 않는다** — 이게 의도된 계약이었다.

M6에서 게임플레이 요구가 바뀌었다: **대쉬로 통과하면 데미지는 없되 탄은 사라져야 한다.**

### 해결: 빼는 대신 표시한다

```cpp
struct FREHitTarget
{
    ARECharacterBase* Player;
    FVector           Location;
    bool              bInvulnerable = false;   // 추가
};
```

**데미지 면제 책임이 수집부에서 소비부로 옮겨간다.**

- `REBulletHitProcessor`: `bInvulnerable`이면 `TakeDamage`만 건너뛰고 **소멸과 폭발은 그대로**
- `REArcHitProcessor`: 같은 목록을 쓰므로 **가드가 없으면 곡사탄 스플래시가 대쉬 무적을 뚫는다**

### 규모 실측

| 유지 탄환 | 대쉬 1회 소멸 |
|---:|---:|
| 348 | 3 |
| 2,929 | 18 |

밀도에 거의 비례. 상한 45,000 외삽 시 **약 280발** — 안전선 200보다 크다. **외삽이라 확정이 아니다.**

## 10. 이슈 #106 / #107 — 연쇄로 발견한 두 결함

#102 검증 중 대쉬 거리가 간헐적으로 2배가 되는 걸 발견했다. 처음엔 #102의 회귀로 보였다(dev 0/13 vs 브랜치 8/14).

### 반증한 가설 다섯

| 가설 | 반증 |
|---|---|
| 폭발 스폰 부하 | 이상 런에서 폭발 **0회** |
| 데미지 유무 | 무적 dev도 안정 |
| 탄환 순회 CPU | 탄 0에서도 재현 |
| 이중 대쉬 | 로그 시퀀스 동일 |
| 프레임 부하 | 대쉬 창 프레임시간 동일 |

### 여기서 저지른 오진 하나

CSV를 600프레임 캡처하고 **"히치 없음"** 이라 단정했다.

**`-csvCaptureFrames`는 프레임 수이지 시간이 아니다.** 헤드리스 `-nullrhi`는 1,800fps로 돌아서 600프레임이 **0.33초**뿐이었다. t=2.0초의 대쉬가 **캡처 밖**이었다.

창을 맞추자 이상 런에만 **290ms 프레임이 정확히 하나** 있었다.

> **교훈**: 프레임 수로 창을 잡을 때는 fps를 곱해 **실제 시간**을 확인해라.

### #106 — 대쉬가 고정거리가 아니었다

주석은 이렇게 적혀 있었다:

> 시간형 RootMotion — 고정속도 × 고정시간 → 마찰 무관 **고정거리**

**실제로는 고정거리가 아니었다.**

`ApplyRootMotionConstantForce`는 힘을 매 이동 틱에 적용한다. 그런데 CMC는 **긴 프레임 하나를 통째로 시뮬레이션**하므로, 소스의 남은 지속시간을 넘겨서도 그 프레임 전체에 힘이 적용된다.

```
거리 = DashStrength × 실제 경과시간   (지속시간이 아니라)
```

| | 지속시간 | 거리 |
|---|---|---|
| 정상 | 0.200s | 678 |
| 히치 겹침 | 0.376s | **1274** |

`ApplyRootMotionMoveToForce`(목표 지점 수렴)로 교체 → 게이트 이탈 **8/13 → 0/8.**

### #107 — 그 290ms의 정체

```
LogStreaming: FlushAsyncLoading(191): 1 QueuedPackages
  AddPackage: /Game/FX/NS_REBulletExplosion
    -> /Niagara/DefaultAssets/DefaultSpriteMaterial
    -> /Niagara/DynamicInputs/...  (수십 개)
```

첫 폭발에서 `LoadObject`가 **동기 로드**를 걸었다. Niagara 시스템 하나가 의존 패키지 수십 개를 끌어온다.

나머지 프레임이 0.5~1.1ms이므로 **300배**다.

월드 시작 시 선로드로 옮겼다:

| | 게임 시작 후 `FlushAsyncLoading` | 게임 중 최장 프레임 |
|---|---|---|
| 전 | 1회 | **290ms** |
| 후 | **0회** | 105~122ms(부팅 직후 첫 프레임) |

> **히치 하나가 전혀 무관해 보이는 시스템을 망가뜨렸다.** 대쉬 거리가 2배가 된 건 대쉬 코드가 아니라 에셋 로드 타이밍 때문이었다.

## 11. 이슈 #100 — 플레이어 HUD

### 만든 것

`UREPlayerHudWidget` — 좌상단에 HP / 대쉬 쿨다운 / 화면상 투사체 수.

기존 위젯들과 같이 **순수 C++ `WidgetTree` 구성**이다(BP 자산 없음).

### 레이아웃 함정

`VerticalBox`를 그대로 루트로 두면 **뷰포트 슬롯이 화면 전폭으로 늘려** 바가 화면을 가로지른다. `Overlay` + `SizeBox`로 좌상단에 고정하고 폭을 묶어야 한다.

실측 스크린샷에서 확인하고 고쳤다.

### 투사체 수는 게임 UI가 아니다

**데모 계측**이다. 포트폴리오 문구("N개의 투사체")를 영상이 스스로 증명하게 하려고 띄운다. ISM 인스턴스 수를 세므로 **화면에 실제로 그려지는 수**다.

### 영상용 CVar 3종

| CVar | 용도 |
|---|---|
| `re.Debug.CheatPanel 0` | 치트 패널 토글 차단 (촬영 중 오조작 방지) |
| `re.Debug.ScreenMessages 0` | 엔진 온스크린 경고 억제 |
| `re.Debug.ScreenshotUI 1` | 스크린샷에 화면공간 UI 포함 |

> `re.Debug.ScreenshotUI` 기본값이 0인 이유: #97의 탄막 렌더 검증에서는 HUD가 화면을 가리면 탄 색·밝기 판정을 방해한다.
>
> **월드스페이스 위젯(보스 체력바)은 0에서도 찍힌다.** 그래서 "UI는 나오는데 HUD만 없다"로 오해하기 쉽다.

### 🔴 대쉬 쿨다운이 죽어 있었다

쿨다운 UI를 붙이려고 잔여시간을 물었더니 **대쉬 직후에도 항상 0.00**이었다.

`REGE_DashCooldown`이 태그를 **5.8에서 폐기된** `InheritableOwnedTagsContainer`로 달고 있었다. GAS가 매 활성마다 경고를 냈다:

```
Warning: CooldownGameplayEffectClass 'REGE_DashCooldown' grants no tags.
```

**경고 그대로 GAS는 쿨다운 태그를 빈 것으로 취급했다.**

겉으로는 멀쩡했다. 즉시 재시도가 막히고 2.1초 뒤 재활성되니 프로브가 통과했다. **하지만 그 차단이 쿨다운 때문인지 어빌리티가 아직 활성 중이라서인지 구분되지 않는 상태였다.**

`UTargetTagsGameplayEffectComponent`로 이관 → `1.97 → 0.00` 카운트다운 확인.

> **이관 중 크래시 하나**: `FindOrAddComponent`는 내부에서 `NewObject`를 부르므로 **CDO 생성자에서 쓰면 죽는다**. `ObjectInitializer.CreateDefaultSubobject`를 써야 한다.

## 12. 이슈 #112 — 데디 우클릭 이동

직접 클라 두 개를 띄워 플레이해보고 나온 문제다. **클라 1명일 때부터 거의 안 움직인다.**

### 측정

| | 0.5초 진행 | 서버 폰 속도 |
|---|---|---|
| 스탠드얼론 | 212.5 | 512 |
| 데디 + 헤드리스 클라 | 7.7 | **0 (전 구간)** |
| 데디 + 실 클라 | **14.9** | 약 62uu/s |

설계값 600uu/s의 **1/10.**

### 원인 (M4 설계 문서가 이미 규명해둠)

원격 클라의 폰은 `RemoteRole == ROLE_AutonomousProxy`다. 이 경우 **서버는 틱에서 `PerformMovement`를 부르지 않는다** — 클라의 `ServerMove` RPC를 기다린다.

그런데 **패스팔로잉(우클릭 이동)은 그 `PerformMovement`에 얹혀 있다.**

이 프로젝트는 입력 예측을 안 쓴다(클릭 지점만 보내고 서버가 패스팔로잉). 그래서 **클라 CMC에 재생할 입력이 없고**(`Acceleration = 0`), 서버는 사실상 전진하지 못한다.

**리슨서버/스탠드얼론은 같은 폰이 로컬 제어라 다른 분기를 탄다 — 그래서 지금까지 안 보였다.**

### 배제한 것

- **틱레이트 아님** — 스탠드얼론을 `t.MaxFPS 30`(데디와 동일)으로 묶어도 207 이동
- **NavMesh 아님** — 목표 투영 성공, 맵 밖은 정상 거부

### 해결: 이동목표를 클라에 복제

M4 설계 문서가 후보로 올려두고 **"측정 후 부족하면 그때 승격"** 으로 보류했던 안이다. 측정이 부족을 증명했으므로 승격했다.

```cpp
UPROPERTY(Replicated)  FVector_NetQuantize MoveTarget;
UPROPERTY(Replicated)  bool bHasMoveTarget;
// COND_AutonomousOnly — 본인만 받는다
```

- 서버: nav 검증 후 목표 설정. **패스팔로잉 상태가 `Moving`이 아니게 되면 해제** — 도달·발사정지·사망·경로실패를 한 곳에서 덮는다
- 오너 클라: 목표 방향으로 `AddMovementInput` → **클라 CMC에 실제 입력이 생겨** `ServerMove`가 가속을 싣고 온다

**14.9 → 234.3.** 스탠드얼론(212.5) 수준.

> **남는 주의**: 클라 예측은 **직선**이다. 서버 패스팔로잉이 곡선 nav 경로를 타면 어긋나고 서버 보정이 정정한다. 지금 아레나는 장애물이 없어 실질적으로 항상 직선이지만, 장애물이 들어가면 재확인이 필요하다.

### 판정 도구가 또 못 잡고 있었다

`dedi-verify`는 이동 **거리를 검사하지 않았다.** `이동 프로브 기동`은 **로그 존재만** 본다. 서버가 폰을 거의 못 움직여도 16항목 전부 PASS였다.

`Assert-Progress` 추가 — 남은거리의 **최솟값**을 본다.

> 마지막 값이 아니라 최솟값을 쓰는 이유: **발사 프로브가 이동을 끊는다**(설계대로). 끊긴 뒤 로그는 계속 같은 값이라 마지막 값은 무엇을 재는지 흐려진다.
